# ADR-007：多代理引入条件（先测量，后拆分）

- 状态：已接受
- 日期：2026-10-18
- 关联：`docs/agent-harness-blueprint/07-planning-and-multi-agent.md`、`13-floodmind-gap-analysis.md`（G-22）、`14-adoption-roadmap.md`（ADR-07）

## 背景

FloodMind 已有进程内委派机制（`SubAgent` / `ParallelTask`），但此前没有收益基线，无法判断某个任务是否值得拆分。蓝图明确不建议为了“多代理”引入框架，缺的是契约与证据。

单代理在上下文连续、事实需要原样保留、改动范围小的任务上通常更可靠；拆分会引入任务交接、上下文复制、汇总失真与额外 token。没有对照数据时，把拆分开成默认路径只会放大这些成本。

## 决策

1. 默认保持单代理执行；`SubAgent` / `ParallelTask` 保持为模型按需选择的工具，而不是默认编排路径。
2. 不引入多代理框架、调度层或跨进程协议。
3. 用 `benchmarks/multi_agent/` 的固定任务集与 single / delegated 两种策略做对照，按以下规则判断某类任务是否值得拆分：

```text
success_ok    = delegated 成功率 >= single 成功率
efficiency_ok = delegated/single token 比值 <= 0.9 或耗时比值 <= 0.9
worth_splitting = success_ok 且 efficiency_ok 且 delegated 成功率 > 0
                  且 delegated 实际发生委派
```

分类汇总额外统计“single 成功但 delegated 失败”的逐任务退化；存在退化即判定该分类不建议拆分，避免聚合成功率掩盖任务间交换。

4. 只有对照结果持续满足规则时，才考虑把拆分策略固化到产品路径；固化前不改变默认行为。

## 理由

- 拆分收益依任务类型差异很大：独立子任务、可并行读取、超长日志隔离可能受益；强上下文写作、单文件小改动通常受损。
- 先有可重复的测量机制，才能区分“拆分没收益”与“拆分实现有问题”。
- 保持子代理为工具而非默认路径，避免在无证据时改变现有单代理行为与成本结构。

## 后果

- 基线结果依赖模型、提示词与任务 fixture；更换其中任一项后必须重新测量，不沿用旧结论。
- 每个任务默认只运行一次，适合发现明显退化与建立基线，不适合估计小方差差异；需要更稳定结论时应增加重复次数并比较分布。
- 默认 CLI 只列任务，不调用模型；`--live` 才会读取模型配置并产生真实费用。
- 未实际发生委派的 delegated 运行不能作为“拆分有收益”的证据。

## 重新评估的触发条件

满足任一条件时重新评估多代理拓扑：

- 在代表性任务集上，delegated 连续多轮满足判定规则，且收益来自可复现的并行或上下文隔离；
- 出现单代理无法满足的硬约束（强隔离、独立权限域、长时后台执行）；
- 任务规模增长导致单代理墙钟时间或上下文预算成为瓶颈，且有测量数据支持。

届时需要先补齐：结构化任务包与返回契约、子代理失败与取消传播、汇总质量评估、成本归因。

## 备选方案

| 方案 | 未采用的原因 |
|---|---|
| 默认启用多代理编排 | 无收益证据；交接与汇总成本可能高于收益 |
| 引入多代理框架 | 现有子代理机制已够用，缺的是契约与证据，不是框架 |
| 强制所有任务走 SubAgent | 会损害上下文密集型任务，且无法按任务类型区分 |
