# 架构边界与核心准入

适用范围：SDK 的新增能力、模块移动、依赖和公共协议变化。本文约束开发方向，不声明新的运行时能力。

## 依赖方向

- 公共 SDK 负责宿主入口与生命周期装配；native Agent 与执行器组织运行，运行时服务执行具体策略。
- `floodmind/agent/runtime/contracts/` 集中数据协议，不依赖业务服务或宿主 UI。
- 工具通过 ToolSpec/AgentTool 接入，权限、输出边界和执行语义由运行时服务提供；不得让工具反向操纵执行循环。
- Provider 适配、MCP、Skill、插件和业务能力应停留在各自边界；不能通过全局变量或私有字段形成隐式双向依赖。
- SDK 保持原生实现与宿主无关；不引入 DSH、A2A、LangChain 或 web/TUI 作为核心依赖。

现有结构依据：公共 SDK 入口 `floodmind/agent/api.py`、`floodmind/agent/native/`、`floodmind/agent/runtime/contracts/`、`floodmind/agent/runtime/services/`。本约束不是一个已启用的全仓静态依赖检查器，评审仍须检查实际 import 和调用方向。

## 进入核心的条件

提交者必须说明：为什么现有工具、插件、Skill、MCP 或宿主组合不能承载；为什么所有宿主都需要此能力；状态归谁所有；失败/取消/并发/恢复如何处理；新增协议有哪些消费者。局部业务需求不能仅因方便而进入执行器。

## 变更程序

1. 明确唯一状态/协议权威，列出生产者、转换层、持久化、恢复和展示消费者。
2. 对语义变更先给出契约及失败回归，再修改实现；架构取舍落 ADR，操作步骤留教程。
3. 直接迁移消费者，不新增双写、隐式 fallback、并行历史源或兼容别名来隐藏分歧。
4. 用最小模块化改动完成职责，不把跨层逻辑堆进现有入口。
5. 提供 [验证矩阵](../testing/change-matrix.md) 要求的证据，并更新结构文档/知识图谱（结构有变时）。

## 禁止模式

- 业务模块读取执行器私有状态以绕开公共协议。
- 同一转换/验证在多个消费者中独立实现。
- 将持久化失败吞为成功，或将超时等同于取消和回滚。
- 用全局可变状态传播实例生命周期，或写真实用户目录作为测试夹具。
- 不经消费者核查就改事件、工具结果、存储格式或公开签名。

验收时必须指出真实调用链和相关回归；文档评审不替代权限、状态恢复和产物测试。
