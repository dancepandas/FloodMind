# 08. 模型网关

> 所属：Agent Harness 建设蓝图 / 第二部分 横向能力
> 版本：v1.0-draft（2026-10-18）
> 核心问题：如何让上层只面对一套稳定语义，而底层可以自由替换供应商与模型。

## 1. 网关的六项职责

| 职责 | 说明 | 失败后果 |
|---|---|---|
| 传输 | 连接、鉴权、超时、代理 | 长回答被截断、无法取消 |
| 编解码 | 请求构造、流式解析、方言适配 | 工具调用错乱、思考块丢失 |
| 装配 | 把流式增量拼成完整消息 | 半截 JSON、重复内容 |
| 能力 | 声明并校验模型能力 | 用不支持的功能，静默降级 |
| 路由 | 选模型、重试、回退 | 成本失控、质量抖动 |
| 计量 | token、成本、缓存命中 | 无法归因与优化 |

网关不是“HTTP 客户端封装”。它是控制面与供应商之间的适配层。

## 2. 规范消息模型

### 2.1 保留原生块

内部消息应保留供应商原生语义：

```text
Message
  role: user | assistant | system | tool
  blocks:
    - TextBlock(text)
    - ToolUseBlock(id, name, input, partial?)
    - ToolResultBlock(tool_use_id, content, is_error)
    - ThinkingBlock(text, signature?)
    - ImageBlock(source, media_type)
    - CacheControlBlock(ttl?)
```

不要过早压平成字符串。压平会丢失：

- 工具调用的结构化参数；
- 思考块与签名（影响后续轮次）；
- 图像与附件引用；
- 缓存断点。

### 2.2 转换边界

```
上层 canonical  ──codec──▶  供应商请求
上层 canonical  ◀─codec──  供应商响应
```

codec 负责：

- 字段映射与默认值；
- 角色与系统提示位置差异；
- 工具 schema 转换；
- 结束原因归一；
- 错误码归一。

codec 不负责：重试、路由、业务逻辑。

## 3. 流式装配

流式响应是增量事件序列，装配是一个显式状态机。

### 3.1 需要处理的事件

| 事件 | 处理 |
|---|---|
| 消息开始 | 建立消息，记录模型与请求 ID |
| 文本增量 | 追加到当前文本块 |
| 工具调用开始 | 建立工具块，记录 id 与 name |
| 工具参数增量 | 追加 JSON 片段，不解析 |
| 工具调用结束 | 解析完整 JSON，校验 schema |
| 思考增量 | 追加到思考块 |
| 用量更新 | 累加 token |
| 结束 | 归一结束原因 |
| 错误 | 分类，决定是否可重试 |

### 3.2 常见缺陷

| 缺陷 | 后果 |
|---|---|
| 每收到一个参数片段就解析 JSON | 必然失败或产生错误中间态 |
| 文本与工具调用顺序被重排 | 模型下一轮理解错乱 |
| 用量只在结束时读 | 超时/中断时丢失计量 |
| 思考块未保留 | 多轮推理质量下降 |
| 结束原因未归一 | 上层无法区分“正常结束”和“被截断” |

### 3.3 装配测试

用录制的事件序列做回放测试，覆盖：

- 纯文本；
- 单工具调用；
- 多工具调用并行；
- 参数跨多个片段；
- 文本与工具交错；
- 思考 + 文本；
- 中途错误；
- 空响应；
- 超长响应。

## 4. 能力表

能力表必须是“可执行的声明”，不是装饰。

| 能力 | 用途 | 缺失时的行为 |
|---|---|---|
| `context_window` | 预算与压缩 | 必须报错，不能猜 |
| `max_output_tokens` | 输出预留 | 使用保守默认并告警 |
| `tool_call` | 工具调用 | 禁用工具或换模型 |
| `parallel_tool_calls` | 并行调用 | 串行化 |
| `reasoning` | 思考块 | 不发送相关参数 |
| `vision` | 图像输入 | 拒绝图像或转文本 |
| `streaming_usage` | 流式用量 | 结束时补算 |
| `prompt_cache` | 缓存 | 不依赖缓存优化 |
| `structured_output` | 结构化输出 | 使用工具或解析兜底 |

要求：

- 每个模型显式声明，不靠前缀猜测；
- 注册表有默认值与覆盖规则；
- 运行时消费这些位，而不是只存不用；
- 能力缺失时行为明确（拒绝/降级/告警），不能静默。

FloodMind 的能力表基本只用到 `context_window`，且默认注册表不设置它，其他能力位未被消费 [B: `docs/knowledge-graph/07-model-layer.md` 5]。这是典型的“声明与执行脱节”。

## 5. 重试与重放安全

### 5.1 重试前置判断

重试前必须回答两个问题：

1. 响应是否已经开始？如果已开始，重试会造成重复输出或重复扣费。
2. 该请求是否可安全重放？如果包含不可逆副作用（工具已在服务端执行），不能重放。

因此网关需要两个标志：

```python
class RetryAdvice:
    response_started: bool
    replay_safe: bool
```

FloodMind 的 `TransportRetryAdvice` 设计了这两个字段，但从未赋值 [B: `07-model-layer.md` 6]。这会导致“不可安全重放却重试”的隐患。

### 5.2 退避策略

- 指数退避 + 抖动；
- 区分错误类型：限流、超时、5xx、鉴权、参数错误；
- 鉴权与参数错误不重试；
- 总重试时长有上限；
- 重试必须可被取消打断。

### 5.3 流式请求的重试

流式请求一旦开始输出，通常不应整体重试。可选策略：

- 保留已输出内容，向用户报告中断；
- 从断点续传（若供应商支持）；
- 重新生成并标记覆盖，但需用户知情。

## 6. 超时与取消

| 超时 | 建议 | 说明 |
|---|---|---|
| 连接 | 5-10s | 快速失败 |
| 首 token | 30-60s | 区分“模型慢”和“连接坏” |
| 总生成 | 按任务配置 | 长回答需要更长 |
| 空闲 | 30s | 流中断检测 |

要求：

- 超时可配置，不硬编码；
- 取消立即中断底层连接；
- 取消后不再重试；
- 超时与取消产生不同终态。

FloodMind 的 LLM 超时硬编码 90s，且重试不可中断 [B: `07-model-layer.md` 6]，属于需要在网关层统一解决的问题。

## 7. 路由与回退

### 7.1 路由维度

| 维度 | 例子 |
|---|---|
| 任务类型 | 规划用强模型，摘要用便宜模型 |
| 上下文长度 | 超长输入走长窗口模型 |
| 能力需求 | 需要视觉/工具/结构化输出 |
| 成本预算 | 超预算降级 |
| 时延要求 | 交互式优先低延迟 |
| 区域/合规 | 数据驻留 |

### 7.2 回退

回退不是无条件换模型。要求：

- 回退目标能力兼容（至少支持工具调用）；
- 回退后提示词与工具 schema 仍有效；
- 回退事件被记录并可观测；
- 回退有次数上限，避免连锁降级；
- 关键任务回退需告警。

### 7.3 不要做的事

- 不要用“模型名前缀”猜供应商能力；
- 不要在同一 run 内静默切换模型导致行为不一致；
- 不要把路由逻辑散落在业务代码里。

## 8. 提示缓存

提示缓存能显著降低长系统提示与工具定义的成本。要求：

- 稳定前缀在前，动态内容在后；
- 缓存断点显式标记；
- 不插入时间戳、随机 ID；
- 记录缓存读取与写入 token；
- 缓存失效时不影响正确性，只影响成本。

注意：不同供应商的缓存语义不同（自动 vs 显式断点，TTL 不同）。网关应归一为“可缓存段”概念，而不是暴露供应商细节。

## 9. 计量与成本

### 9.1 必须记录

| 字段 | 用途 |
|---|---|
| 输入 token | 成本 |
| 输出 token | 成本 |
| 缓存读/写 token | 成本优化 |
| 推理 token（如有） | 成本 |
| 模型与供应商 | 归因 |
| run/step/attempt | 归因 |
| 时延（首 token、总时长） | 体验 |
| 结束原因 | 质量分析 |

### 9.2 归因层级

```
conversation → task → run → thread → step → attempt
```

没有归因就无法回答“哪个功能最贵”“哪次重试浪费了钱”。

### 9.3 预算执行

- 每个 run 有 token/金额预算；
- 接近上限时告警或压缩；
- 超限时停止并给出明确终态；
- 预算检查在执行前，不是事后统计。

## 10. 错误分类

| 类别 | 例子 | 可重试 | 上层处理 |
|---|---|---|---|
| 鉴权 | 401/403 | 否 | 提示配置错误 |
| 参数 | 400 schema | 否 | 修请求 |
| 限流 | 429 | 是 | 退避 |
| 服务端 | 5xx | 是 | 退避/回退 |
| 超时 | 连接/读 | 视情况 | 判断是否已开始 |
| 内容过滤 | 拒绝生成 | 否 | 换策略 |
| 上下文超限 | 400 context | 否 | 压缩后重试一次 |
| 解析失败 | 流格式异常 | 可能 | 记录并终止 |

## 11. 测试

| 测试 | 方法 |
|---|---|
| 方言一致性 | 每个 provider 的录制响应回放 |
| 流式装配 | 事件序列单元测试 |
| 能力声明 | 声明与请求参数一致性检查 |
| 重试安全 | 模拟“已开始响应”后失败 |
| 取消 | 取消后连接关闭、无后续写入 |
| 计量 | 与供应商账单抽样对账 |
| 缓存 | 稳定前缀命中率回归 |

## 12. 成熟判据

- [ ] 上层只依赖 canonical 消息模型；
- [ ] 流式装配有状态机与回放测试；
- [ ] 能力表被真实消费；
- [ ] 重试前判断 `response_started` 与 `replay_safe`；
- [ ] 超时可配置，取消可中断；
- [ ] 路由与回退有策略、有记录、有上限；
- [ ] 缓存布局稳定，命中率可观测；
- [ ] 成本可按 run/step 归因；
- [ ] 预算可执行、可中断；
- [ ] 错误分类统一，上层无需理解供应商差异。
