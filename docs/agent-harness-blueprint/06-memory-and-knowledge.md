# 06. 记忆与知识

> 所属：Agent Harness 建设蓝图 / 第二部分 横向能力
> 版本：v1.0-draft（2026-10-18）
> 核心问题：什么值得跨请求保留、如何写入、如何找回、如何避免越用越脏。

## 1. 记忆的分类

沿用认知科学的四分法，并映射到工程实现：

| 类型 | 内容 | 生命周期 | 工程载体 |
|---|---|---|---|
| 工作记忆 | 当前任务状态、待办、临时变量 | 一次 run | RunState / 任务文件 |
| 情景记忆 | 具体经历：做过什么、结果如何 | 天到月 | 事件日志、经验库 |
| 语义记忆 | 事实、偏好、约定、领域知识 | 长期 | 结构化存储 + 向量/图 |
| 程序记忆 | 如何完成某类任务 | 长期 | 技能、playbook、脚本 |

四类不能用一套机制处理。常见错误是把所有内容塞进向量库，结果是情景记忆污染语义检索，程序知识无法版本化。

## 2. 记忆不等于上下文，也不等于 RAG

| 能力 | 输入 | 输出 | 关键问题 |
|---|---|---|---|
| 上下文工程 | 当前状态 | 本次请求的消息 | 预算与信号密度 |
| RAG | 查询 + 文档库 | 相关片段 | 召回率与切分 |
| 记忆 | 经历与事实 | 可注入的条目 | 写什么、何时更新、如何遗忘 |
| 文件/笔记 | 显式写入 | 原文 | 组织与一致性 |

RAG 是“读文档”，记忆是“读自己”。把记忆做成只写不读的日志，或只读不写的缓存，都不是记忆系统。

## 3. 记忆生命周期

```
感知 → 抽取 → 判定（ADD/UPDATE/DELETE/NOOP）→ 存储
     → 检索（多路召回）→ 重排 → 注入 → 反馈
     → 衰减/归档 → 删除/失效
```

每一步都必须有明确的触发条件与失败处理。

### 3.1 写入触发

| 触发 | 优点 | 风险 |
|---|---|---|
| 每轮结束 | 覆盖全 | 噪声多、成本高 |
| 任务完成 | 情景完整 | 长任务中丢失中间事实 |
| 显式工具调用 | 可控 | 依赖模型主动 |
| 人工标记 | 质量高 | 覆盖率低 |

建议组合：任务完成时自动固化 + 模型可显式写入 + 人工可纠正。

### 3.2 抽取

抽取要回答三个问题：

1. 这条信息是否具有跨请求价值？
2. 它是事实、偏好、决策还是过程？
3. 它的适用范围是什么（用户、项目、会话、全局）？

抽取失败的典型表现：把一次性指令（“这次用中文回答”）写成长期偏好；把临时路径写成项目约定。

### 3.3 判定与固化

Mem0 的做法是两阶段：先抽取候选事实，再对每条事实检索相似项，由模型判定 ADD / UPDATE / DELETE / NOOP [B: Mem0, arXiv:2504.19413]。这是目前最可操作的固化管线。

关键设计：

- 判定必须有相似项作为上下文，否则无法发现冲突；
- UPDATE 必须是“替换 + 保留历史”，不能静默覆盖；
- 判定失败时应丢弃而不是直写，避免污染；
- 需要记录来源（哪个 run、哪条事件）以便追溯。

### 3.4 冲突与时间有效性

事实会变化：用户换了技术栈、项目改了约定、接口废弃。

两种处理：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 覆盖式 | 新值替换旧值 | 简单 | 丢失历史，无法回答“当时是什么” |
| 双时间 | 记录事件时间与写入时间，旧值失效但不删除 | 可追溯 | 查询复杂 |

Zep/Graphiti 采用双时间知识图：每条边同时记录事件发生时间与摄入时间，支持“在某时刻什么是真的” [B: Zep, arXiv:2501.13956]。

本文判断：项目约定、用户偏好这类会变化的事实，至少应保留“失效时间”，而不是直接删除。

### 3.5 遗忘

遗忘不是可选功能。没有遗忘的记忆系统会在几个月内变成噪声库。

| 机制 | 做法 | 适用 |
|---|---|---|
| 时间衰减 | 检索分数乘以时间因子 | 情景记忆 |
| 访问频次 | 长期未命中则降权 | 语义记忆 |
| 置信度衰减 | 多次被反驳则降级 | 冲突事实 |
| 归档 | 移出主检索，保留可查 | 历史经历 |
| 硬删除 | 合规要求 | 用户数据 |

删除必须是真删除或可验证的失效，不能只是“标记为不显示”。

## 4. 存储选型

| 存储 | 擅长 | 不擅长 | 适用 |
|---|---|---|---|
| 向量库 | 语义相似 | 精确条件、关系、时间 | 语义召回 |
| 关系库 | 事务、结构化查询、审计 | 模糊匹配 | 事实表、配置、审计 |
| 图库 | 多跳关系、时间边 | 运维复杂度 | 实体关系、依赖 |
| 文件 | 可读、可版本化、可人工编辑 | 并发、检索 | 项目约定、技能、笔记 |
| 事件日志 | 完整历史、可重放 | 低延迟查询 | 情景记忆的底座 |

推荐组合而不是单一存储：

```
事件日志（事实底座）
  ├─ 语义事实表（结构化，可查询）
  ├─ 向量索引（语义召回）
  ├─ 图索引（关系与时间）
  └─ 文件（人可读的约定与技能）
```

索引是派生，可重建；事实底座不可丢。

## 5. 三种主流架构

### 5.1 分层分页（MemGPT / Letta）

把上下文当作内存，把外部存储当作磁盘：

| 层 | 内容 | 进入上下文方式 |
|---|---|---|
| Core Memory | 人设、用户关键事实 | 始终在系统提示中 |
| Recall Memory | 对话历史 | 检索 |
| Archival Memory | 外部知识 | 工具调用分页读入 |

特点是模型通过记忆编辑工具主动管理自己的记忆 [B: MemGPT, arXiv:2310.08560]。

适用：长期陪伴、个人助理、需要 Agent 自主整理记忆的场景。
风险：模型自编辑可能导致记忆漂移，需要版本与审计。

### 5.2 抽取-更新管线（Mem0）

```
messages → LLM 抽取候选事实 → 检索相似 → LLM 判定操作 → 写入
```

特点：写入时做冲突消解，读取时只做检索。适合多会话、事实密集的应用。

厂商报告在 LoCoMo 上相对基线有显著提升，并大幅降低 p95 延迟与 token 消耗 [B: arXiv:2504.19413，数字为厂商自报]。

### 5.3 时间知识图（Zep / Graphiti）

```
episode → 实体/事实（带双时间）→ 社区摘要
检索：向量 + BM25 + 图遍历 → RRF/MMR 重排 → 上下文
```

特点：能回答“什么时候成立”“和谁有关”。适合业务数据与对话混合、需要审计的场景。

厂商报告在 DMR/LongMemEval 上有提升 [B: arXiv:2501.13956，数字为厂商自报]。

### 5.4 选型建议

| 需求 | 建议 |
|---|---|
| 快速接入个人化 | 抽取-更新管线 |
| 需要时间与关系查询 | 时间知识图 |
| 长期自主代理 | 分层分页 + 显式工具 |
| 合规与可解释优先 | 结构化事实表 + 人工审核 |

本文判断：不要直接采用某个框架的整套记忆模型。先定义自己的事实 schema 与适用范围，再选择存储与算法。

## 6. 数据模型建议

最小语义事实表：

```sql
fact(
  id            TEXT PRIMARY KEY,
  scope         TEXT NOT NULL,      -- user / project / session / global
  subject       TEXT NOT NULL,      -- 实体
  predicate     TEXT NOT NULL,      -- 关系或属性
  object        TEXT NOT NULL,      -- 值
  confidence    REAL NOT NULL,
  valid_from    TIMESTAMP,
  valid_to      TIMESTAMP,          -- NULL 表示当前有效
  recorded_at   TIMESTAMP NOT NULL,
  source_run    TEXT,
  source_event  TEXT,
  status        TEXT NOT NULL       -- active / superseded / deleted
)
```

配套：

- `fact_history`：每次变更的审计；
- `fact_embedding`：向量索引，派生；
- `fact_entity`：实体归一（同一用户的不同写法）；
- `memory_policy`：scope 的读写权限与保留期。

## 7. 检索与注入

### 7.1 多路召回

| 通道 | 擅长 | 权重来源 |
|---|---|---|
| 向量相似 | 语义近似 | 相似度 |
| 关键词/BM25 | 精确术语、ID | 匹配度 |
| 结构化过滤 | scope、时间、状态 | 硬条件 |
| 图遍历 | 关联实体 | 跳数与边权 |
| 最近使用 | 当前任务相关 | 时间衰减 |

### 7.2 重排

- 融合排序（RRF）避免单一分数尺度；
- 多样性（MMR）避免注入十条同义事实；
- 时间与置信度作为特征，而非硬过滤；
- 最终注入条数有上限，且按 token 预算截断。

### 7.3 注入格式

每条注入内容应带：

```
[fact] 用户偏好使用 pnpm（置信度 0.9，来源 run-123，2026-09-12 确认）
```

要求：

- 标注来源，便于模型判断可信度；
- 标注时间，避免把旧事实当现状；
- 冲突事实同时呈现或明确标注已失效；
- 不要把整段历史塞进系统提示。

## 8. 评估

### 8.1 基准

| 基准 | 测什么 | 局限 |
|---|---|---|
| LoCoMo | 长对话问答（单跳、多跳、时间、常识、对抗） | 公开样本少，答案键有错误报告 |
| LongMemEval | 长期记忆的多类型任务 | 场景偏助理 |
| DMR | 对话记忆检索 | 规模有限 |

重要警告：主流记忆基准的头部数字多为厂商自报，独立复现有限；LoCoMo 曾被审计发现约 6.4% 答案键错误，且评测提示不一致会导致分数大幅波动 [D: 多方复核与社区分析]。

### 8.2 应自建的指标

| 指标 | 定义 |
|---|---|
| 写入精确率 | 写入条目中真正有长期价值的比例 |
| 冲突处理正确率 | UPDATE/DELETE 判定与人工标注一致的比例 |
| 检索命中率 | 需要的事实是否被召回 |
| 注入有效率 | 注入内容被模型实际使用的比例 |
| 过期事实残留率 | 已失效事实仍被检索到的比例 |
| 记忆导致的错误率 | 因错误记忆产生的错误回答比例 |
| 存储增长 | 每千轮新增条目数 |
| 删除合规性 | 删除请求的完成时间与覆盖面 |

### 8.3 评测方法

- 构造带时间线的对话，注入事实变更；
- 在后续问题中检查是否使用最新事实；
- 注入干扰事实，检查是否被误用；
- 对比“有记忆/无记忆”的任务成功率与成本；
- 定期人工抽检写入质量。

## 9. 隔离与隐私

| 维度 | 要求 |
|---|---|
| 用户隔离 | 检索必须带 user scope，禁止跨用户 |
| 项目隔离 | 项目约定不能泄漏到其他项目 |
| 会话隔离 | 临时上下文不进入长期记忆 |
| 租户隔离 | 存储层逻辑或物理隔离 |
| 删除权 | 支持按用户/条目删除，且索引同步 |
| 导出 | 支持导出全部记忆 |
| 加密 | 传输与静态加密 |
| 审计 | 谁写入、谁读取、谁删除 |

OWASP 2025 把“向量与嵌入弱点”列为独立风险，包括跨租户相似度泄漏、嵌入反演、未授权写入 [A: OWASP LLM08]。

## 10. 常见失败模式

| 失败 | 表现 | 根因 | 修法 |
|---|---|---|---|
| 记忆污染 | 错误事实被反复使用 | 写入无判定 | 固化管线 + 置信度 |
| 过度检索 | 每轮注入大量无关条目 | 召回无阈值 | 重排 + 上限 |
| 陈旧事实 | 用户已改偏好仍用旧值 | 无失效机制 | 双时间 + 覆盖 |
| 无限增长 | 存储与延迟持续上升 | 无遗忘 | 衰减 + 归档 |
| 情景/语义混淆 | 一次性指令变长期规则 | 抽取无 scope 判断 | scope 分类器 |
| 记忆泄漏 | A 用户看到 B 的事实 | 检索缺过滤 | 强制 scope 过滤 |
| 不可解释 | 不知道为什么记住 | 无来源 | 来源与事件引用 |
| 写入抖动 | 同一事实反复增删 | 判定不稳定 | 阈值 + 幂等键 |

## 11. 与技能、经验的关系

- 情景记忆积累到一定数量后，可归纳为程序记忆（技能）；
- 技能生成应有质量门槛（样本数、成功率、人工审核）；
- 技能是文件，可版本化、可回滚；
- 不要让模型直接把单次成功经验固化为技能，否则会把偶然当规律。

FloodMind 的经验树 → 技能草案路径符合这一模式，并设置了“至少 2 条叶子且高质量占比达标、不覆盖已有文件”的门槛 [B: `docs/knowledge-graph/05-memory.md` 4]。需要补的是技能质量评估与回滚。

## 12. 成熟判据

- [ ] 四类记忆有明确载体，不混用；
- [ ] 写入有抽取、判定、来源记录；
- [ ] 支持 UPDATE 与失效，不静默覆盖；
- [ ] 检索多路召回 + 重排 + 上限；
- [ ] 注入带来源、时间、置信度；
- [ ] 有遗忘与归档机制；
- [ ] 作用域隔离可验证；
- [ ] 删除可传播到所有索引；
- [ ] 有自建指标与人工抽检；
- [ ] 记忆变更可追溯到具体 run/event。
