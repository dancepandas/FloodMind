# 14. 采用路线

> 所属：Agent Harness 建设蓝图 / 第三部分 对照与采用
> 版本：v1.0-draft（2026-10-18）
> 目标：把 `13` 中的差距转成有依赖顺序、有验收标准、可回滚的实施路线。
> 执行状态：见 [15-gap-closure-status.md](./15-gap-closure-status.md)。A/B 阶段缺口项已闭合；C1-C5、C7、D5 已落地并有可执行验证；E 阶段仍按 ADR-007 / ADR-008 推迟。

## 1. 排序原则

1. **先正确性与安全**：会产生错误副作用或权限漏洞的问题优先。
2. **再单一事实源**：任何“双写”“双配置”“双契约”先收口。
3. **再契约与可运营**：让系统可测试、可观测、可回归。
4. **再效率**：上下文、成本、工具质量。
5. **最后扩展**：多代理、协议、平台化。

不跳级。没有恢复与评测的系统，增加能力只会扩大故障面。

## 2. 阶段划分

### 阶段 A：正确性收口（P0）

**目标**：消除会产生错误状态或安全漏洞的结构性缺陷。

范围：

| 工作项 | 产出 | 验收 |
|---|---|---|
| A1 写入 fencing | Journal 写入携带 epoch，旧 epoch 被拒绝 | 并发恢复测试：旧 owner 写入失败，且日志有拒绝记录 |
| A2 重试安全 | 填充 `response_started` / `replay_safe`；取消可打断退避 | 模拟“已开始响应后失败”不重试；abort 后 1s 内停止 |
| A3 上下文窗口单一来源 | 能力表设置真实窗口；压缩与硬预算共用 | 启动校验失败即报错；长任务不出现“提前失败/延迟压缩” |
| A4 压缩原子性 | 摘要失败则中止压缩并保留原文 | 注入摘要失败，验证原文完整、事件标记失败 |
| A5 权限默认行为 | 固定 fail-closed；deny 绝对优先 | 属性测试覆盖规则组合与模式组合 |
| A6 凭证隔离 | 沙箱不继承环境；密钥加密或代理 | 沙箱内读取密钥失败；日志无明文 |
| A7 最小 CI | 单元测试 + 关键恢复/权限用例 | 每次提交自动运行；失败阻断合并 |

依赖：A1 依赖现有 lease 机制；A2 依赖 transport 能感知首 token；A3 依赖模型注册表。

风险：

- fencing 会改变写入路径，需要迁移旧日志（只读兼容）。
- 凭证代理涉及部署形态，可能需要先做“环境变量过滤”这一最小版本。

### 阶段 B：契约统一（P1）

**目标**：让契约成为唯一入口，删除“声明与执行脱节”。

范围：

| 工作项 | 产出 | 验收 |
|---|---|---|
| B1 工具输出契约 | 上限、截断/卸载策略、引用读取工具 | 大输出不再进入上下文；读取可复原 |
| B2 工具注册收口 | `MemoryAdd`、`ApplyPatch` 明确注册或删除承诺 | 文档与运行时一致；有测试 |
| B3 技能写入校验 | `UpdateSkill` 读回校验与回滚 | 写入失败不留半成品 |
| B4 MCP 配置统一 | 单一配置格式与路径；错误提示明确 | 用错格式启动即报错 |
| B5 上下文回放 | 记录装配快照或可重建引用 | 任取一个 run 可还原模型输入 |
| B6 子代理契约 | 结构化任务包与返回格式 | 子代理返回可校验；父级可拒绝不合规结果 |
| B7 能力表消费 | 所有能力位在运行时生效或显式拒绝 | 不支持的能力不发请求 |

依赖：B1 依赖 A3；B5 依赖 Journal 事件扩展。

风险：B2 涉及产品语义（模型是否应主动记忆），需要产品决策而不是工程单方面决定。

### 阶段 C：可运营（P2）

**目标**：让团队能判断“是否变好”，并在出问题时定位。

范围：

| 工作项 | 产出 | 验收 |
|---|---|---|
| C1 内部评测集 | 冒烟 20-50、回归 200-500 | 每次发布运行；有基线分数 |
| C2 判定器 | 状态断言优先，LLM 评审校准 | 与人工判断一致率达标 |
| C3 指标 | 结果、轨迹、可靠性、安全、成本 | 可按任务/run/step 下钻 |
| C4 OTel 对齐 | span 与属性遵循 GenAI 约定 | 可在观测后端查询 |
| C5 故障注入 | 崩溃、超时、网络中断、并发恢复 | 纳入 CI，定期运行 |
| C6 发布门禁 | 冒烟 + 回归 + 安全用例 | 不达标不可发布 |
| C7 成本归因 | 按 run/step 记录 token 与金额 | 可回答“哪个功能最贵” |

依赖：C1 依赖 B5（需要可回放的轨迹）；C4 依赖现有 tracing。

风险：评测集容易过拟合；必须保留 held-out 并定期换血。

### 阶段 D：效率与能力（P3）

**目标**：在不牺牲正确性的前提下提升上下文效率与任务能力。

范围：

| 工作项 | 产出 | 验收 |
|---|---|---|
| D1 上下文预算分层 | 各片段预算与淘汰顺序 | 长任务成功率提升，token 下降 |
| D2 渐进披露 | 工具/知识索引 + 按需加载 | 工具描述占用下降 |
| D3 工具评测 | 真实任务集与轨迹指标 | 工具描述变更可量化 |
| D4 记忆治理 | 失效、衰减、归档、质量指标 | 过期事实残留率下降 |
| D5 规划产物 | 计划文件 + 待办 + 验收 | 长任务可跨窗口恢复 |
| D6 路由与回退 | 按任务/成本/能力路由 | 成本下降且质量不降 |

依赖：D1-D3 依赖 C1-C3；D4 依赖 B1/B2；D5 依赖 B6。

### 阶段 E：扩展（P4，按需）

**目标**：只在有明确需求与收益证据时扩展。

候选：

- 多代理拓扑（编排-工人、评估-优化）；
- A2A（跨组织协作）；
- AG-UI（第三方前端）；
- 平台化（托管运行时、托管记忆）。

进入条件：

1. 阶段 A-C 的验收全部达成；
2. 有单代理基线数据；
3. 有明确的业务场景与成本预算；
4. 有迁移与回滚方案。

## 3. ADR 候选

以下决策需要显式记录，不能靠默认：

| ADR | 问题 | 选项 |
|---|---|---|
| ADR-01 | Journal 写入的 fencing 模型 | epoch / token / 单写者代理 |
| ADR-02 | 上下文窗口来源 | 模型注册表 / 运行时探测 / 配置 |
| ADR-03 | 工具输出上限与卸载 | 截断 / 摘要+引用 / 外部对象 |
| ADR-04 | 记忆写入权限 | 模型主动 / 仅后台 / 混合 |
| ADR-05 | 凭证管理 | 环境变量过滤 / vault / 代理 |
| ADR-06 | 评测判定器 | 状态断言 / LLM 评审 / 混合 |
| ADR-07 | 多代理引入条件 | 成本阈值 / 任务类型 / 不引入 |
| ADR-08 | 协议引入 | MCP 仅工具 / 加 A2A / 加 AG-UI |

## 4. 验收标准模板

每个工作项的验收必须可执行：

```yaml
item: A1-write-fencing
acceptance:
  - test: tests/runtime/test_resume_fencing.py::test_stale_owner_rejected
    expected: pass
  - test: tests/runtime/test_resume_fencing.py::test_epoch_monotonic
    expected: pass
  - manual: 并发启动两个 resume，只有一个成功
  - metric: 旧 epoch 写入拒绝次数 > 0（测试环境）
rollback: 配置开关关闭 fencing（仅过渡期）
```

禁止使用“代码已合并”“逻辑正确”作为验收。

## 5. 建议排期与投入

| 阶段 | 相对投入 | 说明 |
|---|---|---|
| A 正确性 | 中 | 改动集中，但需要仔细设计 |
| B 契约 | 中高 | 涉及多模块与文档一致性 |
| C 可运营 | 高 | 评测集与观测需要持续投入 |
| D 效率 | 中高 | 需要实验与对比 |
| E 扩展 | 视需求 | 不建议预先投入 |

阶段 A 与 B 可以部分并行，但 A1-A5 应先于 B5。

## 6. 度量前后对比

在阶段 A 之前记录基线，之后每阶段复测：

| 指标 | 基线 | 目标 |
|---|---|---|
| 恢复后重复副作用次数 | 未知 | 0 |
| 崩溃恢复成功率 | 未知 | > 95% |
| 长任务（> 50 步）成功率 | 未知 | 提升且稳定 |
| 单任务 token | 未知 | 下降 20% 以上（D 阶段） |
| 工具参数错误率 | 未知 | 下降 |
| 发布回归发现时间 | 未知 | 从周级降到小时级 |
| 成本归因覆盖率 | 0 | 100% |

没有基线就先测基线，不要直接定目标。

## 7. 组织与职责

| 角色 | 职责 |
|---|---|
| 架构 owner | 契约、不变量、ADR |
| 运行时 owner | 循环、状态、恢复、沙箱 |
| 能力 owner | 工具、技能、记忆、模型网关 |
| 质量 owner | 评测集、判定器、CI、指标 |
| 安全 owner | 威胁模型、权限策略、红队 |

小团队可以兼任，但“质量”与“安全”不能由功能开发者自己签字。

## 8. 风险与回滚

| 风险 | 缓解 |
|---|---|
| fencing 改动导致旧日志不可读 | 先做只读兼容，再迁移 |
| 评测集过拟合 | held-out + 定期换血 + 人工抽检 |
| 上下文改造导致短期质量下降 | 灰度 + 对比基线 + 可回退开关 |
| 凭证代理影响部署 | 先做环境过滤，再逐步代理 |
| 路线与现有 P0-P8 规划冲突 | 合并为单一路线图，不并行两套 |

仓库中已有 `docs/superpowers/plans/` 下的 P0-P8 规划。本路线不替代它们，应做一次映射：

- 已有计划中已覆盖的项，标注“已排期”；
- 本路线新增的项，补入对应阶段；
- 冲突项以 ADR 决定。

## 9. 完成定义

一个阶段完成，必须同时满足：

- [ ] 所有工作项验收通过；
- [ ] 文档与实现一致（声明即执行）；
- [ ] 有可复现的测试或演练；
- [ ] 有指标或证据；
- [ ] 有回滚方案；
- [ ] ADR 已记录；
- [ ] 下一阶段的依赖已确认。

## 10. 最终建议

对 FloodMind 而言，最高杠杆的三件事是：

1. **闭合 fencing 与重试安全**：直接消除“状态分叉”和“重复副作用”。
2. **建立最小评测与 CI**：让后续所有改动从“凭感觉”变成“有证据”。
3. **统一上下文窗口与工具输出契约**：让长任务从“偶尔能跑”变成“稳定可跑”。

这三件事完成后，再讨论上下文优化、记忆治理、多代理与协议，收益才会稳定。
