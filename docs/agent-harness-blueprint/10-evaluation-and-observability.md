# 10. 评测与可观测性

> 所属：Agent Harness 建设蓝图 / 第二部分 横向能力
> 版本：v1.0-draft（2026-10-18）
> 核心问题：如何证明系统“变好了”，以及在生产中出问题时如何定位。

## 1. 两个不同的问题

| 问题 | 手段 | 时间尺度 | 输出 |
|---|---|---|---|
| 刚才发生了什么？ | 追踪、日志、指标 | 秒到天 | 现场与因果 |
| 系统是否足够好？ | 评测集、判定器、回归 | 天到月 | 分数与趋势 |

追踪不能替代评测：一次成功不代表稳定。评测不能替代追踪：分数下降时仍要知道是哪一步坏了。

## 2. 指标体系

### 2.1 五类指标

| 类别 | 指标 | 说明 |
|---|---|---|
| 结果 | 任务成功率、答案正确率、验收通过率 | 最终效果 |
| 轨迹 | 步数、工具调用数、无效调用率、重规划次数 | 过程质量 |
| 可靠性 | pass^k、超时率、崩溃恢复成功率、重复副作用率 | 稳定性 |
| 安全 | 越权尝试、注入命中、审批拒绝率、数据外带告警 | 风险 |
| 成本 | 输入/输出 token、缓存命中、单任务成本、时延分位 | 经济性 |

### 2.2 pass^k

传统评测只看单次成功。Agent 需要重复性指标：

```
pass^k = 同一任务重复 k 次全部成功的概率
```

τ-bench 引入 pass^k 正是为了解决“一次成功但不可靠”的问题 [B: Yao et al., τ-bench, 2024]。

### 2.3 分层归因

指标必须能下钻：

```
产品 → 任务类型 → 运行 → 步骤 → 工具/模型调用
```

否则只能知道“成功率下降”，无法定位。

## 3. 评测集设计

### 3.1 两类评测集

| 类型 | 目的 | 来源 | 更新 |
|---|---|---|---|
| 公共基准 | 与业界对比、判断模型能力 | SWE-bench、Terminal-Bench、GAIA 等 | 跟随社区 |
| 内部金标集 | 防止回归、贴合真实分布 | 生产轨迹、真实任务 | 持续扩充 |

本文判断：产品决策应主要依赖内部金标集。公共基准回答“模型强不强”，内部集回答“我的系统有没有退步”。

### 3.2 构造原则

- 任务来自真实使用，不是玩具环境；
- 每个任务有可验证结果；
- 允许多条正确路径；
- 覆盖长任务、多工具、失败恢复；
- 包含对抗与边界用例；
- 有 held-out 集，避免对评测过拟合；
- 定期审计答案键（已知基准存在错误标注）。

### 3.3 规模

- 冒烟集：20-50 条，每次提交运行；
- 回归集：200-500 条，每日或发布前；
- 全量集：1000+，每周或版本发布；
- 探索集：人工分析用，不进门禁。

## 4. 判定器

| 判定器 | 适用 | 风险 |
|---|---|---|
| 精确匹配 | 有唯一答案 | 过于严格，拒绝合理变体 |
| 状态断言 | 文件、数据库、API 终态 | 需要可重置环境 |
| 测试套件 | 代码任务 | 测试覆盖不足会被绕过 |
| LLM 评审 | 开放式输出 | 偏差、不稳定、可被讨好 |
| 人工评审 | 高质量样本 | 昂贵、慢 |

要求：

- 判定器本身要评测（与人判断的一致性）；
- LLM 评审需固定模型、提示、温度，并抽样人工复核；
- 优先状态断言而不是文本匹配；
- 判定失败要能区分“真的错”与“判定器错”。

## 5. 轨迹评测

只看最终答案会漏掉：

- 走了危险路径但碰巧成功；
- 用了 50 步完成本应 5 步的任务；
- 调用了不该调用的工具；
- 依赖了不该依赖的记忆。

轨迹指标：

| 指标 | 含义 |
|---|---|
| 步数效率 | 实际步数 / 专家步数 |
| 工具准确率 | 必要工具是否被调用 |
| 无效调用率 | 参数错误、重复调用、无进展 |
| 恢复能力 | 工具失败后是否换方案 |
| 上下文效率 | 有效 token / 总 token |
| 安全事件 | 越权尝试、注入命中 |

轨迹评测可以抽样人工，也可以用 LLM 按 rubric 打分。

## 6. 生产可观测性

### 6.1 必须采集

| 层 | 数据 |
|---|---|
| 模型 | 请求、响应摘要、用量、时延、结束原因、缓存命中 |
| 工具 | 名称、参数摘要、结果摘要、耗时、错误类型 |
| 控制 | 步数、重试、压缩、审批、取消 |
| 子代理 | 父子关系、预算、终态 |
| 状态 | 恢复次数、检查点、对账结果 |
| 安全 | 判定结果、拒绝原因、异常模式 |

### 6.2 OpenTelemetry GenAI 语义约定

关键约定 [A: OpenTelemetry Semantic Conventions for GenAI]：

| 属性 | 用途 |
|---|---|
| `gen_ai.operation.name` | `chat`、`invoke_agent`、`execute_tool`、`invoke_workflow` 等 |
| `gen_ai.provider.name` | 供应商标识（替代已弃用的 `gen_ai.system`） |
| `gen_ai.agent.id` / `.name` / `.version` | 代理身份 |
| `gen_ai.conversation.id` | 会话关联 |
| `gen_ai.request.model` / `gen_ai.response.model` | 模型 |
| `gen_ai.usage.input_tokens` / `.output_tokens` | 用量 |
| `gen_ai.tool.name` / `gen_ai.tool.call.id` | 工具 |
| `gen_ai.input.messages` / `.output.messages` | 内容（需显式开启） |

注意事项：

- 该约定仍处于 development 阶段，属性可能变化；
- 内容捕获默认关闭，需考虑隐私与体积；
- OTel 没有标准成本属性，成本需自定义命名空间；
- agent span 在进程内为 INTERNAL，远程服务为 CLIENT。

### 6.3 采样

- 错误与慢请求全采样；
- 正常请求按比例采样；
- 高风险工具调用全采样；
- 内容捕获可单独采样；
- 采样策略可配置，不写死。

### 6.4 关联

一次运行应能通过一个 ID 串起：

```
conversation_id → run_id → thread_id → step → tool_call → artifact
```

前端、后端、模型、工具、审计使用同一套 ID。

## 7. 回放与调试

| 能力 | 价值 |
|---|---|
| 事件回放 | 重建状态，验证归约 |
| 轨迹查看 | 看清模型看到了什么、做了什么 |
| 请求重放 | 用相同输入复现问题（注意非确定性） |
| 差异对比 | 两个版本的轨迹/成本/结果对比 |
| 快照测试 | 提示词与工具 schema 变更的影响 |

回放要求：

- 记录模型看到的完整上下文（或可重建的引用）；
- 记录工具结果原文或引用；
- 记录版本（提示、工具、模型、reducer）；
- 支持按 run 导出脱敏样本。

## 8. 灰度与门禁

### 8.1 发布门禁

```
单元测试 → 契约测试 → 冒烟评测 → 回归评测 → 灰度 → 全量
```

门禁条件示例：

- 冒烟集成功率不低于基线；
- 回归集无显著下降（统计检验）；
- 成本不超过预算；
- 安全用例零回归；
- 关键轨迹无新增危险模式。

### 8.2 灰度

- 按用户/会话/流量比例；
- 监控成功率、成本、时延、错误率；
- 有自动回滚条件；
- 新旧版本可对比同一任务。

### 8.3 变更类型与评测重点

| 变更 | 重点评测 |
|---|---|
| 换模型 | 结果、成本、时延、工具调用习惯 |
| 改提示 | 冒烟 + 轨迹 |
| 改工具 schema | 工具评测集 + 参数错误率 |
| 改压缩策略 | 长任务成功率 + 上下文效率 |
| 改权限策略 | 安全用例 + 审批通过率 |
| 改框架/协议 | 契约测试 + 故障注入 |

## 9. 公共基准及其局限

| 基准 | 测什么 | 局限 |
|---|---|---|
| SWE-bench / Verified | 真实仓库 issue 修复 | 数据污染风险、测试可能被绕过 |
| Terminal-Bench | 终端端到端任务 | 任务数有限 |
| τ-bench / τ²-bench | 多轮工具与策略遵循 | 模拟用户，场景受限 |
| GAIA | 通用助理多步任务 | 题目公开，易过拟合 |
| OSWorld | 桌面 GUI 操作 | 环境重、速度慢 |

已知风险：多项基准被指出可通过奖励黑客（reward hacking）获得高分而不真正完成任务；部分审计结论尚待独立复现 [D: 社区审计与二手报道]。

使用建议：

- 只用公共基准做方向性判断；
- 不用单一分数做产品决策；
- 关注任务级分解与失败样本；
- 内部金标集优先。

## 10. 工具选型

| 工具 | 定位 | 许可 | 适用 |
|---|---|---|---|
| Langfuse | 追踪 + 评测 + 提示管理 | MIT（核心） | 需要自托管与开源 |
| Arize Phoenix | OTel 原生追踪 + 评测 | Elastic License 2.0 | OTel 生态、需轻量自托管 |
| Braintrust | 评测优先、数据集与实验 | 闭源 SaaS | 评测流程是瓶颈 |
| Comet Opik | 开源评测与追踪 | Apache 2.0 | 需要完全开源 |
| 自建 OTel + 数仓 | 完全可控 | 自担 | 有平台团队 |

选型原则：

- 先确定语义约定（OTel GenAI）；
- 追踪与评测可以分开选；
- 注意许可证（源码可见不等于 OSI 开源）；
- 评估数据驻留与合规。

## 11. 反模式

1. 只有日志，没有指标，故障靠人肉 grep。
2. 只测最终答案，不看轨迹。
3. 评测集来自文档示例，与生产分布无关。
4. 用 LLM 评审但不校验评审器。
5. Trace 里记录完整 prompt 与用户数据，无脱敏。
6. 采样策略写死，关键错误被采样掉。
7. 换模型不跑回归，靠感觉判断。
8. 指标没有归因维度，无法定位。
9. 公共基准分数当 KPI。
10. 没有基线，所有变化都无法判断好坏。

## 12. 成熟判据

- [ ] 指标覆盖结果、轨迹、可靠性、安全、成本；
- [ ] 有内部金标集与 held-out 集；
- [ ] 判定器经过校准；
- [ ] 轨迹可查看、可回放；
- [ ] 遵守 OTel GenAI 语义约定；
- [ ] 内容捕获默认关闭且可脱敏；
- [ ] 采样策略可配置；
- [ ] 有发布门禁与灰度回滚；
- [ ] 变更类型对应评测重点；
- [ ] 指标可按任务/运行/步骤归因。
