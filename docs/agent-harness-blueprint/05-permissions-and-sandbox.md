# 05. 权限、审批与沙箱

> 所属：Agent Harness 建设蓝图 / 第二部分 横向能力
> 版本：v1.0-draft（2026-10-18）
> 核心问题：在模型可能被诱导、代码可能有害的前提下，如何保证副作用可控、可追溯、可停止。

## 1. 威胁模型

先明确对手与失败方式，再谈机制。

| 威胁 | 路径 | 后果 | 对应 OWASP |
|---|---|---|---|
| 直接提示注入 | 用户输入诱导模型越权 | 执行危险动作 | LLM01 |
| 间接提示注入 | 工具结果、网页、文件、MCP 返回内容中含指令 | 模型把数据当指令 | LLM01 |
| 工具投毒 | 工具描述或返回内容被篡改 | 诱导调用或泄露 | LLM03 |
| 凭证窃取 | 沙箱内代码读取环境变量/配置文件 | 账号被接管 | LLM02 |
| 过度代理 | 工具能力或权限超出任务需要 | 影响面放大 | LLM06 |
| 供应链 | 恶意 MCP server、技能、插件 | 任意代码执行 | LLM03 |
| 无界消耗 | 循环、递归、并行爆炸 | 成本或资源耗尽 | LLM10 |
| 数据外带 | 通过合法工具把敏感数据发到外部 | 数据泄露 | LLM02 |

OWASP 2025 把“过度代理”拆成三个根因：功能过度、权限过度、自主性过度 [A: OWASP Top 10 for LLM Applications 2025]。这三者分别对应工具设计、凭证策略与审批策略。

## 2. 纵深防御的四层

| 层 | 作用 | 不能替代谁 |
|---|---|---|
| 策略判定 | 决定允许/询问/拒绝 | 不能替代沙箱 |
| 人类审批 | 对高影响动作确认 | 不能替代策略，人会疲劳 |
| 沙箱 | 限制执行影响范围 | 不能替代策略，合法动作仍可能有害 |
| 审计 | 事后发现与追责 | 不能阻止损害 |

任何单层都不够。把安全寄托在“模型会拒绝”上，等于没有安全边界。

## 3. 策略判定流水线

Claude Code 的六步判定顺序是一个成熟范例，值得抽象为通用模型 [A: Claude Agent SDK, Permissions]：

```
1. hooks            自定义代码，可拒绝或修改请求；deny 在 bypass 模式下仍生效
2. deny 规则        命中即阻止，不可被后续步骤覆盖
3. ask 规则         命中则强制进入人工确认
4. 权限模式         bypass / acceptEdits / plan / dontAsk / auto
5. allow 规则       命中则自动批准
6. canUseTool       未决时交给宿主回调
```

通用化后的规则：

1. **默认拒绝**（fail-closed）：未匹配任何规则的回退到询问，而不是放行。
2. **拒绝优先**：deny 必须先于 allow 求值。
3. **拒绝不可绕过**：任何“跳过”模式都不能绕过硬拒绝。
4. **判定输入结构化**：工具名 + 规范化参数 + 目标资源 + 会话身份。
5. **判定可解释**：返回命中的规则与原因，但不泄露策略全集。
6. **判定可测试**：策略是代码，需要单元测试与回归用例。

FloodMind 已有 `PermissionService` 与 ASK 两条路径 [B: `docs/knowledge-graph/04-runtime-kernel.md` 5.2]。需要核对的是：deny 是否绝对优先、bypass 是否存在、判定是否覆盖 MCP 工具与子线程。

## 4. 审批设计

审批不是“弹一个确认框”。一个可用的审批必须包含：

| 要素 | 要求 | 反例 |
|---|---|---|
| 动作指纹 | 工具 + 规范化参数 + 目标资源 + 会话 | 只显示“是否允许执行命令” |
| 影响范围 | 哪些文件/资源/网络会被触碰 | 只显示命令字符串 |
| 可选项 | 允许一次、本次会话允许、永久允许、修改后重试、拒绝 | 只有“是/否” |
| 过期 | 审批有效期，过期不放行 | 审批挂起数天后自动执行 |
| 绑定 | 执行前校验参数未被替换 | 审批后模型改了参数仍执行 |
| 审计 | 谁、何时、批了什么、理由 | 只记录“用户同意” |

审批 UX 的核心矛盾是疲劳：审批太多，人会无脑点同意；审批太少，风险失控。解决方式是**按副作用分级**，而不是按工具分级：

| 副作用 | 默认策略 |
|---|---|
| 只读、无网络 | 自动允许 |
| 写工作区内文件 | 会话内允许或首次确认 |
| 写工作区外 | 每次确认 |
| 网络请求 | 按域名允许列表 |
| 不可逆操作（删除、发布、转账、部署） | 每次确认 + 影响摘要 |
| 凭证/权限变更 | 每次确认 + 强提示 |

## 5. 权限模式

模式是对“默认自主度”的预设，必须显式切换、可审计：

| 模式 | 行为 | 适用 |
|---|---|---|
| 默认 | 未匹配则询问 | 日常开发 |
| 计划 | 只读，写操作一律询问 | 方案阶段 |
| 自动编辑 | 工作区内文件写入自动允许 | 受控仓库 |
| 不询问 | 永不弹出，未匹配即拒绝 | 无人值守、CI |
| 绕过 | 全部允许，除硬拒绝 | 仅限隔离环境 |
| 自动 | 由策略引擎动态判定 | 成熟策略系统 |

关键：**“不询问”与“绕过”方向相反**。前者 fail-closed，后者 fail-open。生产默认不应是后者。

## 6. 能力与凭证

### 6.1 能力模型

不要给 Agent “一把万能钥匙”。按能力授权：

```
fs.read:workspace
fs.write:workspace/src
net.http:api.example.com
process.exec:python
secrets.read:github_token   # 通常不应授予
```

能力应与工具绑定，而不是与进程绑定。工具声明所需能力，运行时在调用点检查。

### 6.2 凭证不进入沙箱

Anthropic 在 Managed Agents 中的做法值得作为标准 [C: Anthropic, 2026-04]：

- Git 令牌在沙箱初始化时注入到本地 remote，模型不接触令牌；
- MCP 的 OAuth 令牌存放在沙箱外的 vault；
- 工具调用经由代理，代理用会话令牌换取凭证并代为调用；
- harness 本身也不知道凭证内容。

通用原则：

1. 凭证只存在于受控进程或 vault；
2. 沙箱内只能通过代理发起需要凭证的调用；
3. 代理按会话、按工具、按目标做最小授权；
4. 令牌短时有效，可撤销；
5. 模型上下文、日志、工具结果中不得出现凭证。

### 6.3 环境变量与配置

- 沙箱默认不继承宿主环境变量；
- 必需的变量使用允许列表；
- 配置文件中的明文密钥不是可接受方案；
- 子进程、后台任务继承同一套策略。

## 7. 沙箱分层

### 7.1 隔离级别

| 级别 | 机制 | 隔离强度 | 启动成本 | 适用 |
|---|---|---|---|---|
| 进程级 | 用户、cwd、资源限制 | 弱 | 极低 | 可信代码、本地开发 |
| 容器 | namespaces + cgroups | 中（共享内核） | 低 | 受控 CI、内部工具 |
| 用户态内核 | gVisor 等 | 中强 | 中 | 多租户、需兼容性 |
| 微虚拟机 | Firecracker 等 | 强 | 中（可快照预热） | 不可信代码、云端执行 |
| 远程沙箱 | 托管服务 | 强 + 运维外包 | 网络往返 | 生产、弹性 |

证据：E2B 基于 Firecracker；Modal 以 gVisor 为主；Gemini CLI 支持 Seatbelt、Docker/Podman、gVisor、Windows 原生沙箱等多种后端 [A/B: 各项目文档]。冷启动通常在百毫秒级，预热后可更低；相对 LLM 往返，通常不是瓶颈 [D: 厂商数据与社区测量，数值差异较大]。

### 7.2 沙箱必须约束的维度

| 维度 | 默认 | 说明 |
|---|---|---|
| 文件系统 | 只读根 + 可写工作区 | 工作区外写入拒绝 |
| 网络 | 默认关闭 | 按域名/端口允许 |
| 进程 | 资源与数量限制 | 防止 fork 炸弹 |
| 时间 | 墙钟与 CPU 上限 | 防止挂起 |
| 设备 | 不暴露 | 摄像头、GPU 按需 |
| 内核接口 | seccomp/Landlock | 缩小攻击面 |
| 凭证 | 不存在 | 见 6.2 |

Codex 的沙箱模式提供了清晰分级：`read-only`、`workspace-write`、`danger-full-access`，并默认禁用网络 [A: OpenAI Codex Sandbox]。这种“三档 + 网络独立开关”比单一开关更实用。

### 7.3 沙箱不是万能

- 沙箱不能阻止“合法但有害”的动作（例如在允许范围内删除重要文件）；
- 沙箱不能阻止数据通过允许的网络通道外带；
- 沙箱实现本身可能有漏洞；
- 本地沙箱通常无法防御有本地权限的攻击者。

因此必须与策略、审批、审计组合。

## 8. 组合策略

推荐按“动作风险”组合四层：

| 风险 | 策略 | 审批 | 沙箱 | 审计 |
|---|---|---|---|---|
| 低（只读本地） | 自动允许 | 无 | 只读 | 采样 |
| 中（写工作区） | 允许 + 范围限制 | 首次或会话 | workspace-write | 全量 |
| 高（网络、外部写） | 询问 | 每次 | 网络允许列表 | 全量 + 告警 |
| 极高（不可逆、凭证） | 拒绝或强审批 | 每次 + 二次确认 | 隔离 + 代理 | 全量 + 复核 |

## 9. 子代理与后台任务

权限必须向下继承并收紧，不能放宽：

- 子线程继承父 run 的权限上下文，并可进一步限制；
- 子代理不能获得父代理没有的能力；
- 后台任务在独立沙箱中运行，超时与资源上限独立；
- 取消父 run 时，子线程与后台任务必须被终止；
- 子线程的产物回传需经过与父级相同的路径校验。

FloodMind 的子线程流程包含“子权限/路径上下文”与独立工具运行时 [B: `docs/knowledge-graph/04-runtime-kernel.md` 7.2]，方向正确，需验证是否存在权限提升路径。

## 10. 审计

审计日志要求：

- 追加写、不可篡改（或至少可检测篡改）；
- 记录动作、参数摘要、判定结果、判定依据、执行结果；
- 记录身份：用户、代理、子线程、工具来源；
- 敏感字段脱敏，但保留可关联的哈希；
- 可按 run、会话、工具、资源检索；
- 保留期符合合规要求。

审计与追踪的区别：追踪用于调试，审计用于问责。两者可以共用底层事件，但访问控制与保留策略不同。

## 11. 供应链安全

| 对象 | 风险 | 控制 |
|---|---|---|
| MCP server | 恶意实现、过度权限 | 允许列表、版本固定、最小权限、独立进程 |
| 技能包 | 提示注入、隐藏指令 | 来源校验、内容审查、只读挂载 |
| 插件 | 任意代码 | 签名、沙箱、安装审批 |
| 工具依赖 | 供应链攻击 | 锁文件、镜像扫描 |

MCP 尤其需要注意：server 返回的内容是**不可信输入**，必须当作数据而非指令处理。协议不提供信任，信任由客户端策略提供。

## 12. 安全测试

最低要求：

1. 注入用例库：直接注入、间接注入（文件/网页/工具结果）、编码绕过；
2. 越权用例：路径穿越、符号链接、环境变量读取、子进程逃逸；
3. 审批绕过用例：参数替换、指纹碰撞、并发竞态；
4. 恢复用例：崩溃后是否重复执行不可逆动作；
5. 红队演练：给定目标，尝试外带数据或提升权限。

测试必须自动化并进入 CI，不能只做一次性渗透。

## 13. 成熟判据

- [ ] 策略判定 fail-closed，deny 绝对优先；
- [ ] 审批绑定动作指纹，执行前二次校验；
- [ ] 审批可跨重启存活，有超时；
- [ ] 凭证不进入沙箱与模型上下文；
- [ ] 沙箱按风险分级，网络默认关闭；
- [ ] 子线程权限继承且不可提升；
- [ ] 所有高风险动作有审计记录；
- [ ] MCP/技能/插件有来源与版本控制；
- [ ] 注入与越权用例进入 CI；
- [ ] 有红队演练与修复闭环。
