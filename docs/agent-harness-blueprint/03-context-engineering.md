# 03. 上下文工程

> 所属：Agent Harness 建设蓝图 / 第二部分 横向能力
> 版本：v1.0-draft（2026-10-18）
> 核心问题：在固定预算内，如何让模型每一步都看到“最少但足够”的高信号 token。

## 1. 上下文不是历史记录

上下文是本次请求实际发送的 token 集合。它由系统提示、工具定义、记忆、历史、当前输入、检索结果共同拼装，每次请求重新计算。

三个推论：

1. “把完整对话发过去”不是默认正确，只是最省事的实现。
2. 上下文长度与效果不是线性关系。过长会稀释注意力，过短会丢信息。
3. 上下文构造是 harness 的核心职责，不能交给模型或提示词。

## 2. 上下文腐烂与注意力预算

Anthropic 用“context rot”描述随 token 增加而出现的性能退化：模型对上下文中信息的召回能力并非均匀，长上下文中的中段信息更容易被忽略 [C: Anthropic, Effective Context Engineering, 2025-09]。

工程含义：

- 上下文是有限资源，应按“注意力预算”管理，而不是按“窗口上限”管理；
- 关键指令应靠近开头或结尾，避免埋在中段；
- 长工具结果应卸载，只留摘要与引用；
- 重复信息比缺失信息更糟：它会挤占预算并制造冲突。

## 3. 上下文装配管线

推荐把装配拆成七个有序步骤，每步产出可计量的片段：

```
1. 固定前缀    系统身份、行为规范、输出约定
2. 工具清单    只放当前任务需要的工具
3. 项目约定    AGENTS.md / 规则文件（按作用域）
4. 记忆注入    核心事实、召回结果（带来源与置信度）
5. 历史投影    压缩后的对话与工具结果
6. 当前输入    用户消息、附件引用
7. 即时检索    按需拉取的文件片段、日志、文档
```

每一步都应回答：

| 问题 | 目的 |
|---|---|
| 这段内容属于哪一类？ | 便于独立预算与淘汰 |
| 它占用多少 token？ | 预算核算 |
| 它的权威性如何？ | 冲突时谁优先 |
| 它何时过期？ | 缓存与失效 |
| 它能否被引用替代？ | 卸载策略 |

## 4. 预算模型

不要只设一个总上限。建议分层预算：

| 片段 | 建议占比 | 说明 |
|---|---:|---|
| 固定前缀 | 5-10% | 稳定，可缓存 |
| 工具定义 | 5-20% | 工具越多占比越高，需按需裁剪 |
| 记忆 | 5-15% | 超限时降级为摘要 |
| 历史 | 30-50% | 主要压缩对象 |
| 当前输入 | 5-20% | 用户可能粘贴大文件 |
| 输出预留 | 10-25% | 必须显式预留，否则会被截断 |

实现要点：

- 使用模型真实窗口，而不是预设常量；
- 输入预算 = 窗口 - 输出预留 - 安全余量；
- 触发压缩的阈值应低于硬上限（例如 70-75%）；
- 同一系统内窗口来源必须唯一。

FloodMind 现有实现中，压缩触发阈值与硬预算使用不同来源的窗口值，且默认能力注册表从不设置 `context_window`，最终回退到执行器窗口 [B: `docs/knowledge-graph/03-agent-execution.md` 6, `07-model-layer.md` 5]。这会导致“该压不压”或“提前失败”。

## 5. 压缩策略

### 5.1 压缩保留什么

Anthropic 的长期任务实践给出的保留清单值得作为默认基线 [C: 2025-09 / 2026]：

- 架构决策与原因；
- 未解决的 bug 与已知风险；
- 实现细节中不可从代码直接看出的约束；
- 最近改动的文件清单（约 5 个）；
- 当前任务目标与验收标准；
- 用户明确表达的偏好与禁止项。

不应保留：

- 完整的工具输出（留摘要 + 引用）；
- 已经完成的中间推理；
- 重复的报错堆栈；
- 可重新检索的文档原文。

### 5.2 压缩的三种实现

| 实现 | 做法 | 优点 | 风险 |
|---|---|---|---|
| 客户端压缩 | harness 生成摘要，替换消息 | 完全可控 | 需要额外模型调用 |
| 服务端压缩 | API 侧生成压缩块 | 不占客户端逻辑，缓存友好 | 供应商绑定 |
| 结构性压缩 | 删除/裁剪特定类型（旧工具结果） | 确定性、便宜 | 不可恢复 |

Anthropic 的 context editing 提供两类服务端编辑：清理旧 `tool_use/tool_result` 对，以及清理思考块；并报告单独使用约 29% 改善，与 memory tool 组合约 39% [A: Anthropic Context Editing 文档]。其关键设计是编辑发生在缓存查找之后，因此不破坏前缀缓存。

### 5.3 压缩的原子性

压缩必须以“原子组”为单位，禁止把 `tool_call` 与 `tool_result` 拆开。FloodMind 的 `ContextCompressor` 已按 Atomic Group 删除中间段 [B: `03-agent-execution.md` 6]，这是正确设计。

但需补一条：压缩后必须生成摘要。若区间计算失败导致中间段被直接丢弃且无摘要，模型会丢失历史语义。现有文档已把这一点列为风险。

### 5.4 压缩的触发与反馈

- 触发：token 占比、步数、阶段切换（如规划完成进入执行）；
- 反馈：压缩前后的预算报告、被压缩的消息区间、摘要哈希；
- 可逆：原文在日志中，可重新投影；
- 可评测：压缩后任务成功率不应显著下降。

## 6. 卸载与引用

当单个工具结果过大（日志、网页、长文件），正确做法是卸载而非截断：

```
tool.result:
  summary: "构建失败，3 个 TypeScript 错误，主要在 src/auth/*"
  artifact_ref: sha256:...
  size: 18432
  preview: 前 20 行
```

模型需要细节时，通过工具按行号/关键词读取。这比“截断到 2000 字符”更可靠，因为截断可能正好丢掉关键错误。

要求：

- 卸载有阈值与上限；
- 引用可解析、可鉴权、可过期；
- 模型知道如何取回（提供读取工具）；
- 引用本身占用少量 token，不能递归膨胀。

## 7. 渐进披露与即时检索

渐进披露（progressive disclosure）的核心是：不在启动时加载全部知识，而是先给索引，按需展开。

三种形态：

| 形态 | 例子 | 适用 |
|---|---|---|
| 索引 + 读取 | 文件树 + 按需读文件 | 代码库、文档库 |
| 技能清单 + 加载 | 只列技能名与描述，命中后加载正文 | 大量流程知识 |
| 工具分组 + 展开 | 先给工具类别，再给具体工具 | 工具数量大 |

即时检索（just-in-time retrieval）强调在需要时拉取，而不是预先塞入。代价是增加往返次数，收益是上下文更干净。

本文判断：两者应结合使用。稳定且高频的知识预加载，长尾且低频的知识按需检索。

## 8. 结构化笔记与外部状态

长任务不能只依赖上下文记忆。建议维护显式的任务状态文件：

| 文件 | 内容 | 谁写 |
|---|---|---|
| 任务清单 | 待办、进行中、已完成 | 模型通过工具写 |
| 决策记录 | 决策、原因、被否决的方案 | 模型或人 |
| 未解问题 | 阻塞点、待确认项 | 模型 |
| 交接包 | 目标、进度、下一步 | 压缩/重置前生成 |

这些文件的价值在于：它们独立于上下文窗口，可被重新读取，也可被人审查。

Anthropic 的 memory tool 采用类似思路：客户端文件系统下的 `/memories` 目录，模型主动读写，并与上下文清理联动（清理前提示模型先保存）[A: Anthropic Memory Tool 文档]。

## 9. 子代理隔离

子代理的核心价值不是“并行”，而是“隔离上下文”。

规则：

- 子代理拥有独立上下文窗口；
- 只返回蒸馏结果（通常 1000-2000 token），不回传完整轨迹；
- 返回结构固定：结论、证据、未决问题、产物引用；
- 主代理不把子代理的中间步骤放进自己的上下文。

Anthropic 报告多代理系统消耗约 15 倍于普通对话的 token，其中很大部分来自每个 worker 重复携带工具定义与任务框架 [C: Anthropic, Multi-Agent Research System, 2025-06]。这解释了为什么子代理只适合高价值、可并行的任务。

## 10. 缓存友好布局

提示缓存能显著降低成本与时延，但前提是前缀稳定。

布局原则：

```
[稳定] 系统身份 + 行为规范 + 输出格式
[稳定] 工具定义（顺序固定）
[较稳定] 项目规则
[变化] 记忆注入
[变化] 历史
[变化] 当前输入
```

要求：

- 稳定段不插入时间戳、随机 ID、会话 ID；
- 工具顺序确定，不随注册顺序漂移；
- 动态内容尽量后置；
- 压缩/编辑不破坏已缓存前缀（服务端编辑的优势）；
- 记录缓存命中率，作为上下文质量的指标之一。

## 11. 度量

上下文工程不能只靠感觉。建议采集：

| 指标 | 含义 | 目标 |
|---|---|---|
| 输入 token 分布 | 各片段占比 | 无单片段长期超预算 |
| 压缩触发率 | 每 turn 压缩次数 | 稳定，不频繁抖动 |
| 压缩后成功率 | 压缩前后任务完成率 | 无显著下降 |
| 缓存命中率 | 缓存读取 token / 总输入 | 稳定段越长越高 |
| 工具结果平均大小 | 是否失控 | 有上限 |
| 卸载率 | 大结果走引用的比例 | 高 |
| 重复读取率 | 同一引用被反复取回 | 低，说明摘要不足 |
| 上下文利用率 | 有效信息 / 总 token | 人工抽检 |

## 12. 反模式

1. 每次请求都重发全部历史，靠窗口大硬扛。
2. 用字符串截断处理大输出，丢掉关键错误。
3. 压缩只保留最近 N 条，丢掉任务目标。
4. 把工具定义全量加载，几十个工具挤占 30% 预算。
5. 在系统提示里插入时间戳，导致缓存永不命中。
6. 子代理把完整对话回传给主代理。
7. 记忆检索结果无来源、无置信度，模型无法判断可信性。
8. 压缩后不记录摘要，无法复现模型当时看到的内容。

## 13. 成熟判据

- [ ] 有分层预算，而非单一上限；
- [ ] 窗口来源唯一且真实；
- [ ] 压缩按原子组，且必生成摘要；
- [ ] 大结果走卸载 + 引用；
- [ ] 工具按需加载；
- [ ] 技能/知识采用渐进披露；
- [ ] 子代理只回传蒸馏结果；
- [ ] 稳定前缀可缓存，命中率可观测；
- [ ] 压缩与检索策略有 A/B 或回归评测；
- [ ] 上下文构造过程可回放（知道模型当时看到了什么）。
