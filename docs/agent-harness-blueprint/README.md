# Agent Harness 建设蓝图

> 版本：v1.0-draft
> 快照日期：2026-10-18
> 性质：厂商中立的参考架构与能力基线，不是 FloodMind 的实现说明
> 用途：为 FloodMind 的功能完善、架构调整、选型与评审提供对照系

## 1. 这套文档解决什么问题

Agent 项目的多数问题并不来自模型本身，而来自模型之外的工程层：循环控制、上下文构造、工具执行、状态持久化、权限边界、恢复与观测。这套文档把这一层定义为 **harness**，并给出一套从上到下的信息组织方式，使团队可以：

1. 用统一语言描述一个 Agent 系统由哪些层组成；
2. 判断某个能力属于 harness 的哪一层，应该由谁负责；
3. 用成熟度模型定位当前系统，而不是只凭功能清单判断先进与否；
4. 在引入框架、协议或云平台前，明确边界与不可让渡的契约；
5. 对 FloodMind 做逐层差距分析，形成可排序的优化路线。

## 2. 范围与非目标

### 2.1 在范围内

- Agent SDK 与宿主接口；
- 控制循环与状态机；
- 上下文工程与压缩；
- 工具契约、执行、事务与幂等；
- 权限、审批、沙箱与安全；
- 记忆与知识；
- 规划、委派与多代理；
- 模型网关与流式装配；
- 互操作协议；
- 评测、可观测性与运维；
- 上述能力的成熟度与采用路线。

### 2.2 不在范围内

- 模型预训练、微调与推理引擎内部实现；
- 具体业务领域建模（水文、预报、数据分析等）；
- Prompt 文案技巧的穷举；
- 单一厂商产品的功能测评与排名；
- 直接给出 FloodMind 的代码改动。

## 3. 证据等级

本文所有外部结论尽量标注来源与证据等级。等级用于表达可信度，不表达重要性。

| 等级 | 含义 | 典型来源 |
|---|---|---|
| A | 正式规范或官方文档明确声明 | 协议规范、SDK 文档、云平台文档 |
| B | 可验证的源码、论文或公开基准 | GitHub 仓库、论文、评测报告 |
| C | 官方工程博客、设计说明、作者公开演讲 | 工程博客、会议分享 |
| D | 社区总结、二手报道、推断 | 博客综述、论坛、本文作者的归纳 |

写作规则：

- 事实与推断分开表述；推断必须写“推断”或“本文判断”。
- 产品宣传语不当作能力证据。
- 同一结论尽量有第二个来源交叉验证。
- 时效敏感内容标注发布日期；无法确认版本时明确写“截至检索时”。

## 5. 结论速览

供快速阅读，详细论证见对应篇目：

1. Harness 的核心不是“循环 + 工具”，而是**六个契约**（身份、消息、工具、事件、状态、策略）与**十二条不变量**（`01`）。
2. 能用于真实工作的门槛是 **L2 可恢复**：工具调用有唯一终态、崩溃恢复不重复副作用、权限判定在副作用之前（`02`、`12`）。
3. 上下文工程的默认顺序是**卸载 > 修剪 > 压缩**；压缩必须保留架构决策、未解 bug、近期文件与任务目标（`03`）。
4. 工具设计应按**目标**而非底层 API 建模，并把描述当提示词写；工具质量必须用真实任务评测（`04`）。
5. 权限的六步判定中，**deny 必须绝对优先且不可被绕过模式覆盖**；凭证永远不进入沙箱与上下文（`05`）。
6. 记忆的关键不是存储，而是**写入判定、冲突消解、时间有效性与遗忘**（`06`）。
7. 多代理约消耗 15 倍 token，收益来自并行探索；**强耦合任务不应拆分**（`07`）。
8. 模型网关必须让**能力表、重试安全性、计量与预算**真正被执行，而不是只声明（`08`）。
9. 协议只解决互操作，**不解决信任、权限与状态权威**（`09`）。
10. 没有内部评测集与轨迹指标，就无法证明系统变好；公共基准只用于方向判断（`10`）。
11. FloodMind 的结构性成熟度约为 **L2**，运营性约为 **L1-L2**；最高杠杆的三件事是 fencing、重试安全、最小评测与 CI（`13`、`14`）。

## 6. 三种使用方式

### 6.1 设计评审

按 `01` 的层级逐层提问：

- 这一层的职责是否清晰？
- 输入输出契约是否稳定？
- 不变量是否可验证？
- 失败模式是否有对应处理？
- 是否有度量证明它工作？

### 6.2 选型评审

先看 `09` 与 `11`，判断候选方案属于哪一层：

- 它是工具协议、代理协作协议，还是 UI 协议？
- 它替代的是 harness 的哪一层，还是只是某一层的适配器？
- 它把状态、身份、权限放在哪里？
- 引入后是否形成新的不可替换事实源？

### 6.3 差距分析与路线

使用 `12` 打分，使用 `13` 对照 FloodMind，使用 `14` 排序。排序原则：

1. 先修正确性与安全边界；
2. 再统一事实源与契约；
3. 再做上下文与工具效率；
4. 再做多代理与协议；
5. 最后做平台化与生态。

### 6.4 阅读路径

| 角色 | 顺序 | 目的 |
|---|---|---|
| 决策者 | README → 01 → 12 → 13 → 14 | 判断现状、风险与投入顺序 |
| 架构师 | 00 → 01 → 02 → 05 → 08 → 09 → 12 | 建立契约与不变量，做选型 |
| 功能开发者 | 03 → 04 → 06 → 07 → 10 | 改上下文、工具、记忆与评测 |
| 新成员 | 00 → 01 → 11 → appendix-a | 建立全局语言与业界坐标 |

不要从 `11` 的产品清单开始读。先有分层与契约，再看产品属于哪一层，否则容易把“功能列表”误当成“架构方案”。

## 7. 与现有文档的关系

| 文档 | 关系 |
|---|---|
| `docs/knowledge-graph/` | 描述 FloodMind **当前**的结构事实，证据以 `file:line` 为准 |
| `docs/architecture/FM_ARCHITECTURE_BASELINE.md` | 描述 FloodMind 的**目标**架构与非协商不变量 |
| 本目录 | 描述**业界参考系**与能力分层，用于判断目标是否完整、当前差距在哪 |
| `docs/agent-memory-survey.md` | 记忆专题的既有调研，本目录第 06 篇与其互补，不重复其论文清单 |

冲突处理：

- 当前实现以知识图谱与源码为准；
- 目标架构以基线文档为准；
- 业界方案以本目录的来源清单为准；
- 三者不一致时，不应用“业界如此”直接覆盖本地约束，应形成 ADR。

## 8. 维护约定

- 每季度或每次引入新框架/协议时复核来源与版本。
- 新增能力先判断属于哪一层，再决定是否修改文档结构。
- 成熟度评分必须附证据，不能只给分数。
- 不复制大段外部文档；保留链接、版本与关键结论。
- 本文档不承诺任何实现状态；实现状态只写在知识图谱与代码中。
