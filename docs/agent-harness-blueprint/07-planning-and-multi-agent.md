# 07. 规划与多代理

> 所属：Agent Harness 建设蓝图 / 第二部分 横向能力
> 版本：v1.0-draft（2026-10-18）
> 核心问题：什么时候需要显式规划，什么时候值得拆成多个代理，拆分后如何不失控。

## 1. 先问是否真的需要

规划与多代理都会增加复杂度、成本与失败面。采用前先回答：

1. 任务是否长到单窗口无法完成？
2. 是否存在可并行的独立子任务？
3. 是否需要不同工具集/权限/模型？
4. 单代理失败是否主要因为上下文过载而非能力不足？

如果答案多为否，优先做：更好的工具、更好的上下文、更清晰的停止条件。

Anthropic 的立场是：先用最简单的方案，单次调用能解决就不要 workflow，workflow 能解决就不要自主 agent [C: Building Effective Agents, 2024-12]。

## 2. 规划的表示

规划不是一个字符串，而是可被读取、修改、检查的结构。

| 表示 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 自然语言计划 | 灵活 | 不可校验、易漂移 | 短任务 |
| 待办列表 | 可勾选、可恢复 | 粒度粗 | 中等任务 |
| 结构化 DAG | 可并行、可校验 | 前期成本高 | 复杂流水线 |
| 计划文件 | 人可读、跨窗口 | 需模型主动维护 | 长任务 |

推荐：长任务使用“计划文件 + 待办列表”组合。计划文件记录目标、约束、阶段、验收标准；待办列表记录当前进度。

## 3. 规划的生命周期

```
目标澄清 → 分解 → 排序 → 执行 → 观察 → 重规划 → 收敛
```

### 3.1 分解

- 每个子任务有明确的完成判据；
- 子任务之间依赖显式；
- 粒度以“一次可验证的产出”为准，不以“一次工具调用”为准；
- 不确定的部分标记为探索任务，而不是假装已知。

### 3.2 重规划触发

| 触发 | 处理 |
|---|---|
| 子任务失败两次 | 换方案或降级 |
| 发现新约束 | 更新计划文件 |
| 预算消耗超预期 | 缩减范围或暂停 |
| 验收标准不满足 | 回到分解 |
| 上下文即将重置 | 生成交接包 |

重规划必须有上限，否则会陷入“计划-失败-再计划”的循环。

### 3.3 收敛

计划完成不等于任务完成。必须有验收步骤：

- 运行测试/检查；
- 对照验收标准逐条确认；
- 记录未完成项与原因；
- 产出交接摘要。

## 4. 五种工作流模式

Anthropic 归纳的模式仍然是目前最清晰的分类 [C: Building Effective Agents]：

| 模式 | 结构 | 适用 | 不适用 |
|---|---|---|---|
| 提示链 | A → B → C | 步骤固定、可分段验证 | 需要动态分支 |
| 路由 | 分类器 → 专用处理 | 输入类型差异大 | 类型边界模糊 |
| 并行 | 多路同时 → 汇总 | 独立子任务、投票 | 强依赖 |
| 编排-工人 | 主代理分解 → 子代理执行 | 可并行、子任务独立 | 紧密耦合 |
| 评估-优化 | 生成 → 评审 → 修订 | 有明确质量标准 | 无客观标准 |

选择原则：能用固定流程表达就不要让模型决定流程；能让模型在节点内判断就不要让模型设计整个图。

## 5. 单代理与多代理

### 5.1 成本结构

Anthropic 报告：普通对话约 1 倍 token，单代理任务约 4 倍，多代理系统约 15 倍；在研究类任务上，多代理相对单代理提升约 90%，而 token 使用量解释了约 80% 的性能方差 [C: Multi-Agent Research System, 2025-06]。

含义：

- 多代理的收益主要来自“更多并行探索”，不是“更聪明”；
- 成本是结构性的，不是调参能消除的；
- 只有高价值、可并行的任务才划算。

### 5.2 适用与不适用

| 适合 | 不适合 |
|---|---|
| 广度搜索、多源调研 | 强耦合的代码修改 |
| 独立子任务并行 | 需要共享隐含上下文 |
| 不同权限/工具隔离 | 实时协同 |
| 需要独立评审 | 简单问答 |

Cognition 的观点值得引用：不要为“看起来很厉害”而拆分，多代理在需要连续决策与共享上下文的任务上会放大错误 [D: Cognition, Don't Build Multi-Agents, 2025]。这与 Anthropic 的结论并不矛盾：两者都在强调任务结构决定适用性。

### 5.3 判断清单

- 子任务之间是否需要频繁交换中间状态？是 → 不要拆。
- 子任务是否可独立验证？否 → 不要拆。
- 并行能否显著缩短墙钟时间？否 → 收益有限。
- 任务价值是否足以承担数倍 token？否 → 不要拆。

## 6. 拓扑

### 6.1 编排-工人（Orchestrator-Worker）

```
Orchestrator
  ├─ Worker A ─→ 蒸馏结果
  ├─ Worker B ─→ 蒸馏结果
  └─ Worker C ─→ 蒸馏结果
        ↓
   Orchestrator 汇总/补缺
```

要求：

- 工人上下文独立；
- 只回传结构化摘要；
- 编排器负责去重、冲突消解、缺口识别；
- 并发有上限，失败可重派。

### 6.2 交接（Handoff）

控制权与上下文移交给另一个代理，原代理退出或等待。

适用：客服分流、专家转接。
风险：上下文在交接中丢失；需要显式的交接包格式。

OpenAI Agents SDK 把 handoff 作为一等原语，模型可直接选择移交；同时提供 manager 模式（一个代理持有所有工具，通过调用子代理作为工具）[A: OpenAI Agents SDK]。两者区别在于“谁保留控制权”。

### 6.3 层级（Hierarchical）

多层编排。优点是规模，缺点是成本与延迟叠加，且错误会逐层放大。

本文判断：层级超过两层后，调试成本急剧上升。除非任务天然分层，否则不建议。

### 6.4 评估-优化（Evaluator-Optimizer）

生成者产出，评估者按标准打分并给出修改意见，循环直到达标或达上限。

要求：

- 评估标准显式、可复现；
- 评估者与生成者使用不同提示或模型；
- 有最大轮数与收敛判据；
- 评估结果可审计。

### 6.5 辩论/投票

多个代理独立作答，再聚合。适用于有客观答案、需要降低方差的任务。

成本高，且可能“集体犯错”。需要独立性与多样性，否则只是重复同一偏差。

## 7. 子代理契约

子代理不是“再开一个对话”。它需要严格契约：

```yaml
task:
  goal: "定位登录失败的原因"
  scope: ["src/auth/**", "logs/auth.log"]
  constraints: ["只读", "不修改代码"]
  acceptance: ["给出根因", "给出证据文件与行号"]
  budget: {tokens: 50000, wall_clock_s: 300}
  tools: [repo_search, read_file, read_log]
  permissions: {fs.read: workspace, fs.write: none}
return:
  format: structured
  fields: [conclusion, evidence, open_questions, artifacts]
  max_tokens: 2000
```

要求：

- 输入含目标、范围、约束、验收标准、预算、工具与权限；
- 输出结构化、有上限；
- 子代理不能扩大自己的权限；
- 子代理失败要返回可分类的原因；
- 父代理不直接读取子代理的完整轨迹。

## 8. 状态与恢复

多代理系统的状态归属必须清晰：

| 状态 | 归属 | 说明 |
|---|---|---|
| 父 run 状态 | 父日志 | 权威 |
| 子线程状态 | 子日志 | 独立可恢复 |
| 汇总结果 | 父日志事件 | 子线程产物提交后写入 |
| 共享文件 | 工作区/产物存储 | 需并发控制 |
| 临时消息 | 内存 | 不持久化 |

恢复时：

- 父 run 恢复后，先对账子线程状态（完成/失败/孤儿）；
- 已完成子线程的产物不得重复生成；
- 孤儿子线程要么接管，要么终止，不能放任；
- 子线程的 lease/fencing 与父级一致。

FloodMind 的恢复流程包含“对账僵尸事务、审批、子线程、后台任务” [B: `docs/knowledge-graph/04-runtime-kernel.md` 6.2]，方向正确；需要验证子线程产物复制是否幂等。

## 9. 失败模式

| 失败 | 表现 | 根因 | 对策 |
|---|---|---|---|
| 电话游戏 | 信息在层级间失真 | 每层重述 | 传结构化事实与引用，不传转述 |
| 上下文碎片 | 子代理不知道全局约束 | 交接包缺失 | 显式约束与验收标准 |
| 错误放大 | 子代理错误被父级当事实 | 无验证 | 父级抽检 + 证据要求 |
| 重复劳动 | 多个子代理做同一件事 | 分解不清 | 任务去重 + 范围互斥 |
| 成本爆炸 | token 超预期数倍 | 无预算 | 每线程预算 + 全局预算 |
| 死锁等待 | 互相等待对方结果 | 依赖环 | DAG 校验 |
| 孤儿进程 | 父取消后子仍在跑 | 取消未传播 | 取消树 + 看门狗 |
| 汇总偏差 | 只采纳最先返回的结果 | 汇总策略草率 | 结构化对比 + 冲突标注 |

## 10. 编排器设计要点

1. **分解质量决定上限**：子任务边界不清，后面怎么优化都无效。
2. **并发控制**：同时运行的工人数、总 token、总时长都要有上限。
3. **超时与重派**：单个工人超时不应拖垮整体。
4. **结果校验**：检查结构、引用是否存在、是否满足验收标准。
5. **缺口识别**：汇总后判断哪些子问题仍未回答，决定是否补派。
6. **可解释汇总**：最终答案应能追溯到哪些工人、哪些证据。

## 11. 人在规划中的位置

- 高风险任务的计划应可审阅（plan mode）；
- 计划变更超过阈值时重新请求确认；
- 人可以编辑计划，系统必须接受并记录；
- 审批不应细化到每一步，否则失去自主性收益。

## 12. 成熟判据

- [ ] 有明确的“是否需要多代理”判断记录；
- [ ] 计划是结构化、可恢复的；
- [ ] 重规划有触发条件与上限；
- [ ] 子代理有输入输出契约与预算；
- [ ] 子代理只回传蒸馏结果；
- [ ] 并发、超时、取消有上限与传播；
- [ ] 子线程状态可对账、可接管、可终止；
- [ ] 汇总可追溯到证据；
- [ ] 多代理成本可计量、可归因；
- [ ] 有对比单代理的基线数据。
