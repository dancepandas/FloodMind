# 04. 工具契约与 Agent-Computer Interface

> 所属：Agent Harness 建设蓝图 / 第二部分 横向能力
> 版本：v1.0-draft（2026-10-18）
> 核心问题：如何设计模型“用得对、用得省、出错可恢复”的工具界面。

## 1. 工具层的三重责任

工具不是“把函数暴露给模型”这么简单。它同时承担：

| 责任 | 面向谁 | 失败表现 |
|---|---|---|
| 能力暴露 | 模型 | 找不到工具、选错工具 |
| 执行与副作用 | 运行时 | 重复执行、挂起、越权 |
| 结果语义化 | 上下文 | 噪声淹没上下文、模型误读 |

多数工具问题不是实现错误，而是这三层责任混在一起。

## 2. 工具契约的完整字段

建议每个工具定义至少包含以下内容。没有出现在 schema 里的字段，也必须存在于注册表元数据中。

```yaml
name: repo_search                  # 命名空间 + 动作
namespace: repo
description: >
  Search repository content by literal or regex. Use for locating
  definitions; prefer read_file once the path is known.
input_schema:
  type: object
  properties:
    query: { type: string, description: "Literal or regex; no shell syntax" }
    path_glob: { type: string, default: "**/*" }
    max_results: { type: integer, default: 20, maximum: 100 }
  required: [query]
  additionalProperties: false
output:
  format: json                     # json | text | markdown | xml
  schema_ref: repo_search.v1
  max_bytes: 32768
  truncation: summarize_and_offload
side_effects:
  class: read_only                 # read_only | reversible | irreversible
  parallel_safe: true
  idempotent: true
permissions:
  capability: fs.read
  approval: never                  # never | on_write | always
  scope: workspace
lifecycle:
  timeout_ms: 30000
  cancel: cooperative
  retry: { max: 2, backoff: exponential, replay_safe: true }
observability:
  trace_args: [query, path_glob]
  redact: []
```

关键点：

- `additionalProperties: false` 必须显式，否则模型会发明参数。
- `side_effects.class` 决定并发、审批与重试策略。
- `max_bytes` 与 `truncation` 决定上下文是否会被单次调用打爆。
- `replay_safe` 决定崩溃恢复时能否自动重试。

## 3. ACI 设计原则

Anthropic 在工具设计实践中总结出一组可操作的原则，本文将其整理为六条 [C: Anthropic, Writing Tools for Agents, 2025-09]：

### 3.1 面向目标，而非面向 API

不要一比一映射底层 API。先问“Agent 要完成什么”，再设计工具。

反面例子：`list_contacts` 返回全部联系人，模型逐条读。
正面例子：`search_contacts(query)` 直接返回相关结果。

同源建议：用 `search_logs` 替代 `read_logs`，只返回相关行与上下文。

### 3.2 合并高频链路

如果多个调用总是成对出现，合并为一个工具。合并的判断依据来自评测中的调用序列统计，而不是猜。

注意边界：合并过度会让工具参数爆炸，模型难以正确填写。原则是“一个工具对应一个可解释的动作”。

### 3.3 返回高信号，而非全量字段

工具结果应优先返回语义字段，而不是内部标识：

| 低信号 | 高信号 |
|---|---|
| uuid | name |
| 256px_image_url | image_url |
| mime_type | file_type |
| 内部枚举值 | 人类可读状态 |

若下游调用确实需要 ID，提供 `response_format: concise | detailed`，让模型选择，而不是永远返回两套。

### 3.4 为 token 效率设计

- 结果分页，默认页小；
- 长文本用摘要 + 引用；
- 避免重复字段；
- 避免嵌套空对象；
- 输出结构按任务选择（JSON / Markdown / 文本），并以评测决定，而非教条。

Anthropic 明确指出：响应结构（XML/JSON/Markdown）对评测表现有实际影响，不存在通用最优解。

### 3.5 把描述当提示词写

工具描述是模型决策的直接输入。写法：

- 像向新同事解释：术语、查询格式、资源关系都要显式；
- 参数名无歧义：`user_id` 而不是 `user`；
- 说明何时用、何时不用；
- 给出一个真实例子；
- 用严格 schema 约束，而不是靠描述兜底。

证据：Anthropic 报告仅通过精确修改工具描述，就显著降低了错误率并提升了 SWE-bench Verified 表现。

### 3.6 用评测驱动迭代

工具设计必须闭环：

```
生成真实任务 → 跑 Agent → 看轨迹与错误 → 改工具或描述 → 重跑
```

必须采集的指标：

- 任务成功率；
- 工具调用次数与冗余调用；
- 参数校验失败率；
- 工具错误率；
- 单次调用耗时；
- token 消耗；
- 工具选择是否正确（预期工具 vs 实际工具）。

## 4. 命名与命名空间

工具数量增长后，命名直接决定选择准确率。

规则：

1. 命名空间按服务或资源划分：`asana_search`、`jira_search`、`repo_read_file`。
2. 前缀式与后缀式命名效果不同，且因模型而异；应通过自己的评测选择，而不是照搬。
3. MCP 工具需要额外处理：不同 server 可能有同名工具，注册时必须加前缀或做稳定映射。
4. 名称一旦发布，不轻易修改；修改视为破坏性变更。

常见错误：

- 名称过于抽象（`process`、`run`）；
- 名称与描述矛盾；
- 同一能力有两个名字；
- 大小写/分隔符不统一，导致模型拼错。

## 5. 输入校验与执行顺序

推荐固定顺序，任何一步失败都返回结构化错误，不进入下一步：

```
1. 工具存在性
2. 参数 JSON 可解析
3. schema 校验（类型、必填、枚举、范围、additionalProperties）
4. 语义校验（路径存在、ID 格式、资源归属）
5. 权限判定（见 05）
6. 审批（如需）
7. 执行前二次校验（参数指纹一致）
8. 执行
9. 结果归一与上限处理
10. 事件提交
```

为什么校验要在权限之前：避免把畸形参数送进策略引擎，减少策略绕过面；但**资源归属校验**必须在权限判定中或之后再做一次，因为策略需要知道目标资源。

## 6. 错误分类

错误不是字符串，而是可被模型与运行时共同处理的类型：

| 类型 | 例子 | 模型可恢复 | 运行时可重试 |
|---|---|---|---|
| 参数错误 | 缺字段、类型错 | 是（改参数） | 否 |
| 前置条件不满足 | 文件不存在、未登录 | 是（先做别的） | 否 |
| 权限拒绝 | 策略 deny、审批拒绝 | 是（换方案或求助） | 否 |
| 瞬时故障 | 网络超时、限流 | 可能 | 是（带退避） |
| 永久故障 | 服务下线、资源删除 | 否 | 否 |
| 不确定 | 超时但可能已执行 | 需查询状态 | 否，先对账 |
| 内部错误 | 实现 bug | 否 | 有限 |

错误结构建议：

```json
{
  "error": {
    "type": "precondition_failed",
    "message": "File not found: src/auth.ts",
    "retryable": false,
    "hint": "Use repo_search to locate the file",
    "details": {"path": "src/auth.ts"}
  }
}
```

`hint` 对模型恢复极其重要，但要短，且不能泄露策略细节。

## 7. 并发与顺序

| 工具类型 | 并发 | 理由 |
|---|---|---|
| 只读、无共享状态 | 可并行 | 降低时延 |
| 只读但有大结果 | 限并发 | 避免上下文与内存峰值 |
| 可逆写 | 串行或按资源分片 | 避免竞态 |
| 不可逆写 | 严格串行 + 审批 | 避免重复与冲突 |
| 长任务 | 后台化 + 轮询/通知 | 不阻塞主循环 |

Claude Agent SDK 明确规定只读工具可并行、修改型工具必须串行 [A: Claude Agent SDK]。这是可移植的默认策略。

并发还需要“同资源互斥”：两个工具都改同一个文件时，即使都是“可逆写”，也不能并行。

## 8. 工具事务与恢复

工具事务的完整语义见 `02-control-loop-and-durability.md` 第 6 节。这里只强调与工具设计直接相关的三点：

1. 工具必须声明 `idempotent` 与 `replay_safe`，否则恢复时只能标记不确定。
2. 工具应支持幂等键，或提供“查询是否已执行”的伴随能力。
3. 工具的超时必须与取消语义一致；超时后进程可能仍在运行，必须能 kill 或标记为孤儿。

## 9. 工具裁剪与按需加载

工具数量与选择准确率通常负相关。控制手段：

| 手段 | 做法 | 代价 |
|---|---|---|
| 静态分组 | 按角色/任务给不同工具集 | 需要配置 |
| 动态裁剪 | 根据任务阶段只暴露相关工具 | 需要阶段识别 |
| 两级暴露 | 先给类别，再给具体工具 | 增加一次往返 |
| 技能封装 | 把多步流程写成技能，只暴露一个入口 | 灵活性下降 |

本文判断：工具超过约 20-30 个后，必须做分组或裁剪，否则描述本身就会占用大量预算并干扰选择。

## 10. 工具评测

### 10.1 评测集构造

- 任务来自真实工作流，不是玩具沙箱；
- 每个任务有可验证结果（精确匹配或判定器）；
- 允许多条正确路径，不强行规定工具序列；
- 包含需要多次调用的复杂任务；
- 保留 held-out 集，防止对评测过拟合。

### 10.2 评测执行

- 用简单循环程序化运行，每个任务一个 Agent；
- 系统提示要求输出推理与反馈块，便于分析；
- 记录完整轨迹，不只记录最终答案。

### 10.3 从轨迹中看什么

| 现象 | 可能原因 | 修法 |
|---|---|---|
| 不调用某工具 | 描述不清、名称不直观 | 改描述、改名称 |
| 重复调用同一工具 | 分页/上限不合理 | 调参数、合并工具 |
| 参数频繁非法 | schema 模糊、缺例子 | 收紧 schema、加示例 |
| 选错相近工具 | 命名空间混乱 | 重命名、合并或拆分 |
| 结果被误读 | 返回字段低信号 | 改返回结构 |
| 调用次数过多 | 工具粒度过细 | 合并 |

## 11. MCP 工具的特殊性

MCP 把工具来源外部化，带来额外问题：

| 问题 | 影响 | 处理 |
|---|---|---|
| 同名工具 | 注册冲突 | 强制 `server_tool` 命名 |
| schema 质量不可控 | 模型误用 | 本地覆盖描述或做适配层 |
| 信任边界 | 恶意 server 返回注入内容 | 结果视为不可信输入 |
| 超时与取消 | 远端不响应 | 客户端超时 + 断开 |
| 版本漂移 | 工具行为变化 | 固定 server 版本，记录握手能力 |
| 凭证 | server 需要密钥 | 凭证代理，不进入模型上下文 |

协议本身只解决“如何调用”，不解决“是否可信”。信任策略必须在 harness 层实现。

## 12. 技能与工具的分工

| 维度 | 工具 | 技能 |
|---|---|---|
| 本质 | 可执行函数 | 知识与流程说明 |
| 调用 | 模型按 schema 调用 | 模型读取后按说明行动 |
| 失败 | 有明确错误类型 | 无运行时错误，只有理解偏差 |
| 版本 | 需要严格兼容 | 可渐进更新 |
| 适用 | 确定性操作 | 判断密集、步骤多变的任务 |

判断标准：如果步骤固定且需要外部副作用，做成工具；如果步骤需要根据情况调整，写成技能。

技能本身也需要治理：来源、版本、适用范围、是否可写、写入是否校验。可写技能目录必须与只读技能目录分离，写入需要审批或至少读回校验。

## 13. 成熟判据

- [ ] 每个工具有完整契约（输入、输出、副作用、权限、超时、上限）；
- [ ] schema 严格，禁止未声明字段；
- [ ] 错误结构化，含可恢复提示；
- [ ] 只读并行、写操作串行、同资源互斥；
- [ ] 大结果卸载而非截断；
- [ ] 工具数量受控，有分组或动态裁剪；
- [ ] 命名空间稳定，MCP 工具无冲突；
- [ ] 有基于真实任务的工具评测集；
- [ ] 工具描述变更经过评测；
- [ ] 工具调用全链路可追踪、可回放。
