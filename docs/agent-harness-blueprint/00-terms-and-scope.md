# 00. 术语、边界与常见混淆

> 所属：Agent Harness 建设蓝图 / 第一部分 方法论
> 版本：v1.0-draft（2026-10-18）
> 目的：先统一语言，再讨论架构。后续所有篇目使用本文定义，不再重复解释。

## 1. 为什么先定义术语

Agent 工程目前最大的沟通成本不是技术难度，而是同一个词指不同东西。典型例子：

- “记忆”有时指上下文窗口里的历史，有时指跨会话的向量库，有时指项目里的 `AGENTS.md`。
- “会话”有时指一次用户提问，有时指一条持久化的对话记录，有时指模型的一次 HTTP 连接。
- “Agent 框架”有时指循环实现，有时指编排图，有时指一套工具生态。

术语不统一会直接导致架构错误：把上下文压缩当成记忆系统，把日志当成状态，把重试当成恢复。本文把每个词收敛到一个定义，并给出判断标准。

## 2. 核心术语

### 2.1 系统层

| 术语 | 英文 | 定义 | 判断标准 |
|---|---|---|---|
| 模型 | model | 接收消息序列、产生消息或工具调用请求的推理服务 | 无状态、无工具执行权 |
| 宿主 | host | 调用 Agent SDK 的程序，负责界面、配置、生命周期 | 决定“跑在哪” |
| Harness | harness | 模型之外、使 Agent 能持续完成任务的工程层：循环、上下文、工具路由、权限、持久化、观测 | 换模型仍需要它 |
| Scaffold | scaffold | 为特定基准或任务搭建的临时外围结构，可包含 prompt、工具集、验证脚本 | 通常不可复用为产品 |
| Runtime | runtime | harness 中负责执行与状态的部分，强调进程、沙箱、事件、恢复 | 与“内核”近义 |
| 框架 | framework | 提供抽象与组件的库，如 LangGraph、ADK、Agents SDK | 不必然包含持久化与沙箱 |
| 平台 | platform | 托管 harness 的云服务，额外提供身份、运行时、记忆、网关 | 把运维责任转移给供应商 |
| 协议 | protocol | 跨进程/跨组织的接口约定，如 MCP、A2A、AG-UI | 解决互操作，不解决内部架构 |

一句话：**harness 是产品，框架是零件，平台是租来的 harness，协议是插座。**

### 2.2 控制层

| 术语 | 英文 | 定义 |
|---|---|---|
| 轮次 | turn | 一次用户输入到 Agent 给出最终响应的完整过程，可包含多个 step |
| 步 | step | 一次模型调用及其产生的工具调用与结果 |
| 尝试 | attempt | 针对同一步的一次具体模型请求；重试产生新 attempt |
| 调用 | call | 一次工具调用请求，必须与一个结果或一个明确的失败终态配对 |
| 循环 | agent loop | 组装上下文 → 调模型 → 解析输出 → 执行工具 → 回填结果的重复过程 |
| 停止条件 | stopping condition | 正常完成、最大步数、预算耗尽、策略拒绝、取消、不可恢复错误 |
| 规划 | planning | 在执行前或执行中生成、修订任务分解 |
| 编排 | orchestration | 决定由哪个执行单元在何时做什么，包括路由、并行、汇总 |
| 交接 | handoff | 把控制权与上下文移交给另一个 Agent 或子线程 |
| 人机协同 | HITL | 在关键动作前暂停，等待人类批准、修改或拒绝 |

### 2.3 状态层

| 术语 | 英文 | 定义 |
|---|---|---|
| 会话 | session | 跨多个 turn 的持久化交互容器，是恢复与审计的单位 |
| 运行 | run | 一次从开始到终态的 Agent 执行，通常对应一个 turn 或一个任务 |
| 线程 | thread | 运行内部可独立调度的执行分支，子代理运行在其中 |
| 事件 | event | 已发生事实的不可变记录，追加写入，带序号与类型 |
| 日志 | journal / event log | 事件的权威存储，唯一事实源 |
| 归约器 | reducer | 从事件序列确定性推导状态的纯函数 |
| 投影 | projection | 由状态或事件派生出的只读视图，如聊天历史、UI 列表 |
| 检查点 | checkpoint | 某一序号的完整状态快照，用于加速恢复 |
| 恢复 | resume | 从日志重放或检查点继续执行，不重复已产生的副作用 |
| 重放 | replay | 重新消费事件以重建状态；不是重新执行副作用 |
| 重试 | retry | 对失败步骤再次请求；与恢复不同，可能产生新副作用 |
| 幂等 | idempotent | 同一请求执行多次与执行一次的效果相同 |
| 隔离栅栏 | fencing | 用 epoch/token 阻止旧持有者继续写入 |

### 2.4 能力层

| 术语 | 英文 | 定义 |
|---|---|---|
| 工具 | tool | 模型可请求调用的确定性能力，有名称、参数模式、结果契约 |
| 工具契约 | tool contract | 工具规范、调用、结果、错误、权限、超时、输出上限的完整约定 |
| ACI | Agent-Computer Interface | 面向模型的交互界面设计：动作粒度、反馈格式、可恢复性 |
| 技能 | skill | 可复用的任务知识与操作说明，通常是提示词与脚本的组合，不是可执行函数 |
| MCP | Model Context Protocol | 连接 Agent 与外部工具/资源/提示的开放协议 |
| 记忆 | memory | 跨 turn 或跨会话保留并可检索的信息，区别于上下文窗口 |
| 上下文 | context | 本次模型请求实际携带的 token 集合 |
| 压缩 | compaction | 用摘要替换较早上下文，保留可恢复性 |
| 修剪 | trimming | 直接删除部分上下文（如旧工具结果），通常不可恢复 |
| 工作记忆 | working memory | 当前任务内的临时状态，通常存在于 RunState |
| 情景记忆 | episodic memory | 具体经历与事件，带时间与情境 |
| 语义记忆 | semantic memory | 抽取后的事实、偏好、约定，去情境化 |
| 程序记忆 | procedural memory | 如何做某类任务的步骤与技能 |
| 固化 | consolidation | 把原始经历抽取、去重、合并为长期条目的过程 |

### 2.5 执行与安全层

| 术语 | 英文 | 定义 |
|---|---|---|
| 沙箱 | sandbox | 限制代码与命令影响范围的执行环境 |
| 权限闸门 | permission gate | 对工具调用做 allow/ask/deny 判定的组件 |
| 审批 | approval | 人类对某次具体动作的授权，应绑定动作指纹而非自然语言 |
| 能力 | capability | 进程或代理被授予的最小权限集合，而非全量凭证 |
| 凭证代理 | credential broker | 在不向沙箱暴露密钥的前提下代执行外部调用 |
| 审计 | audit | 可追溯、不可篡改地记录谁在何时做了什么 |

### 2.6 保障层

| 术语 | 英文 | 定义 |
|---|---|---|
| 追踪 | trace | 一次执行的因果树，含模型、工具、子代理 span |
| 指标 | metric | 成功率、时延、token、成本、工具错误率等可聚合数值 |
| 评测 | evaluation | 用数据集与判定器衡量能力与回归 |
| 轨迹评测 | trajectory eval | 评判执行路径是否合理，而不仅看最终答案 |
| 金标集 | golden set | 内部维护的、与生产分布一致的回归用例集 |
| 灰度 | canary | 小流量验证新模型、新提示、新工具 |

## 3. 十二组必须分清的概念

### 3.1 Workflow 与 Agent

- Workflow：路径由代码预先确定，模型只在节点内做局部判断。
- Agent：路径由模型在运行时决定，代码提供工具与边界。

判据：如果去掉模型后流程仍然成立，它是 workflow；如果去掉模型后无法决定下一步，它是 agent。

业界共识是先用最简单的方案：单次调用能解决就不要 workflow，workflow 能解决就不要自主 agent [C: Anthropic, Building Effective Agents, 2024-12]。

### 3.2 Harness 与 Framework

Framework 提供抽象，Harness 承担责任。判断一个库是不是 harness，看它是否同时处理：循环终止、上下文预算、工具事务、权限、恢复、观测。只提供 `Agent` 类和工具装饰器的库是 framework。

### 3.3 上下文与记忆

上下文是“这次请求带了什么”，记忆是“系统在任何时刻能找回什么”。

- 上下文有硬上限，按 token 计费，每次请求重新组装。
- 记忆是外部存储，通过检索或工具调用进入上下文。

把记忆直接塞进系统提示不是记忆系统，只是上下文构造的一种策略。

### 3.4 会话与上下文窗口

会话是持久化容器，可以远大于上下文窗口。把“会话历史”等同于“模型看到的全部历史”会在长任务中直接失效。

Anthropic 的 Managed Agents 明确把 session 定义为“存在于上下文窗口之外、可被查询的事件日志”，harness 只保证它持久且可读 [C: Anthropic, Scaling Managed Agents, 2026-04]。

### 3.5 压缩、摘要、修剪、卸载

| 手段 | 是否保留原文 | 是否可恢复 | 适用 |
|---|---|---|---|
| 压缩 compaction | 生成摘要替换 | 原文若已持久化则可恢复 | 长对话、跨阶段任务 |
| 摘要 summarization | 生成新文本 | 否 | 阶段性交接 |
| 修剪 trimming | 直接删除 | 否 | 旧工具结果、旧思考块 |
| 卸载 offload | 移到外部存储，留引用 | 是 | 大输出、日志、文件 |

顺序建议：先卸载，再修剪，最后压缩。Anthropic 把“清理旧工具结果”列为最安全的手段 [C: Anthropic, Effective Context Engineering, 2025-09]。

### 3.6 工具、技能、MCP Server

- 工具是可执行函数，模型按 schema 调用。
- 技能是知识与流程说明，通常按需加载到上下文，不直接执行。
- MCP Server 是工具/资源/提示的提供方，通过协议暴露，不等于工具本身。

三者可以互相包装，但责任不同：工具负责“能做”，技能负责“知道怎么做”，MCP 负责“从哪里来”。

### 3.7 子代理与子线程

- 子线程是调度与隔离单位，拥有独立 journal、沙箱、配额。
- 子代理是运行在子线程中的 Agent 实例，拥有独立上下文。

子线程可以跑非 Agent 任务；子代理一定需要子线程或等价隔离。

### 3.8 检查点、快照、日志

- 日志是事实，按事件追加。
- 快照是某时刻的状态副本，可能不完整。
- 检查点是带版本与游标的快照，必须能与日志对齐后使用。

只有检查点没有日志，无法判断快照之后发生了什么；只有日志没有检查点，恢复会变慢但语义正确。

### 3.9 重试、恢复、重放

- 重试：同一步再来一次，可能重复副作用。
- 恢复：从持久状态继续，要求已完成的工作不重复。
- 重放：重新归约事件，不执行副作用。

三者混用是生产事故的常见来源：把“重放”写成“重新执行工具”，或在响应已开始后重试。

### 3.10 权限、审批、沙箱

- 权限：策略层判断“允不允许”。
- 审批：人类对具体动作的授权。
- 沙箱：即使被允许，也只能在受限环境里执行。

三者是纵深防御，不可互相替代。沙箱不能替代审批（合法但高影响的操作仍需确认），审批不能替代沙箱（人可能批准了被注入诱导的动作）。

### 3.11 可观测性与评测

可观测性回答“刚才发生了什么”，评测回答“系统是否足够好”。Trace 不能替代评测集，评测集也不能替代生产追踪。

### 3.12 平台能力与自建能力

平台提供的是运维与集成，不自动提供正确的架构。采用平台前必须确认：状态归谁、身份归谁、权限归谁、迁移成本是多少。

## 4. 范围边界

本蓝图讨论 harness 的工程结构，不讨论：

- 模型训练与推理优化；
- 业务领域知识建模；
- 具体 prompt 文案；
- 厂商产品排名。

## 5. 使用本文的判断清单

在阅读后续篇目前，先用五个问题定位任何 Agent 系统：

1. 唯一事实源是什么？是消息数组、数据库行，还是事件日志？
2. 一次工具调用失败后，系统如何知道它是否已经产生副作用？
3. 上下文超限时，系统丢什么、留什么、能否找回？
4. 谁有权阻止一个危险动作？阻止发生在执行前还是执行后？
5. 换一个模型或换一个框架，哪些契约必须保持不变？

答不上来的层，就是后续差距分析的重点。
