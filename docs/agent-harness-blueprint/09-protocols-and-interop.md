# 09. 协议与互操作

> 所属：Agent Harness 建设蓝图 / 第二部分 横向能力
> 版本：v1.0-draft（2026-10-18）
> 核心问题：哪些协议解决哪一层的问题，引入后会不会制造第二个事实源。

## 1. 协议地图

| 协议 | 连接 | 解决的问题 | 不解决的问题 |
|---|---|---|---|
| MCP | Agent ↔ 工具/资源/提示 | 工具接入标准化 | 权限、信任、状态 |
| A2A | Agent ↔ Agent | 跨组织任务协作 | 内部编排、上下文管理 |
| AG-UI | Agent ↔ 前端 | 流式事件与状态同步 | 执行、持久化 |
| Agent Protocol | 客户端 ↔ Agent 服务 | 统一任务 API | 语义与能力差异 |
| 厂商 API | 应用 ↔ 平台 | 托管运行时、会话、记忆 | 可迁移性 |
| OpenTelemetry GenAI | 运行时 ↔ 观测后端 | 追踪与指标语义 | 评测、审计 |

协议是插座，不是电器。选了插座不代表电器能工作。

## 2. MCP

### 2.1 架构

- JSON-RPC 消息；
- 有状态连接；
- 客户端与服务端能力协商；
- 服务端提供 tools / resources / prompts；
- 客户端提供 sampling / roots / elicitation。

传输：stdio（本地）与可流式 HTTP（远程）。远程场景涉及授权。

### 2.2 版本要点

| 版本 | 关键变化 |
|---|---|
| 2025-06-18 | 结构化工具输出、移除 JSON-RPC 批处理、OAuth Resource Server 定位、Resource Indicators、elicitation、resource links |
| 2025-11-25 | sampling 支持工具调用参数、URL 模式 elicitation、schema 增强 |

证据等级 A：规范原文与变更日志。

### 2.3 授权

MCP 把服务端定位为 Resource Server，授权委托给外部 Authorization Server（OAuth）。要点：

- 客户端不应直接持有长期凭证；
- 令牌应限定资源与范围；
- 远程 server 必须校验令牌受众；
- 本地 stdio server 的信任模型不同，不能照搬。

### 2.4 接入时的工程问题

| 问题 | 处理 |
|---|---|
| 工具名冲突 | 注册时加 `server_tool` 前缀 |
| schema 质量差 | 本地覆盖描述或做适配层 |
| 返回内容不可信 | 视为数据，不当指令 |
| 超时/断连 | 客户端超时、重连、降级 |
| 能力漂移 | 固定版本，记录握手能力 |
| 凭证 | 代理或 vault，不进入上下文 |
| 工具数量膨胀 | 按需连接、分组暴露 |

### 2.5 MCP 不是安全边界

协议本身不提供：

- 服务端可信度；
- 工具行为的正确性；
- 数据外带防护；
- 权限最小化。

这些必须由 harness 的策略层与沙箱层提供。把 MCP server 当作可信组件，是当前最常见的安全误区。

## 3. A2A

### 3.1 核心对象

| 对象 | 含义 |
|---|---|
| Agent Card | 代理元数据：名称、描述、URL、能力、技能、安全方案 |
| Task | 一次协作任务，有生命周期状态 |
| Message | 任务中的消息，由 Part 组成 |
| Part | 文本、数据、文件等片段 |
| Artifact | 任务产出，可增量流式 |
| TaskStatusUpdateEvent | 状态变更事件 |
| TaskArtifactUpdateEvent | 产物更新事件 |
| PushNotificationConfig | 客户端注册的回调 |

Agent Card 通常发布在 `/.well-known/agent-card.json`。

### 3.2 交互

- `sendMessage` / `sendMessageStream`：发起任务或消息；
- `getTask`：查询状态；
- `cancelTask`：取消；
- 订阅/重订阅：断线后可恢复流；
- 推送通知：HTTP POST 到客户端 webhook，至少一次投递，客户端需幂等。

### 3.3 设计要点

- 任务状态是权威，事件是增量；
- 多流订阅需保证事件顺序一致；
- 产物可增量，但最终必须可校验（ID、名称、完整性）；
- 推送与流式是两条路径，可能重复，客户端必须去重。

### 3.4 适用判断

A2A 适合：

- 跨团队/跨组织的代理协作；
- 需要标准化任务生命周期与产物的场景；
- 代理作为服务被外部调用。

不适合：

- 单个进程内的多代理编排（用内部接口更简单）；
- 需要共享细粒度状态的协作（A2A 面向任务，不面向共享内存）。

## 4. AG-UI

### 4.1 定位

AG-UI 是 Agent 与前端之间的事件协议，通常走 SSE（也支持 WebSocket）。可以把它理解为“前端侧的 MCP”。

### 4.2 事件族

| 族 | 事件 |
|---|---|
| 运行生命周期 | RUN_STARTED / RUN_FINISHED / RUN_ERROR |
| 步骤 | STEP_STARTED / STEP_FINISHED |
| 文本 | TEXT_MESSAGE_START / CONTENT / END |
| 工具 | TOOL_CALL_START / ARGS / END / RESULT |
| 状态 | STATE_SNAPSHOT / STATE_DELTA / MESSAGES_SNAPSHOT |
| 推理 | 思考/推理事件 |
| 中断 | 人机协同中断事件 |
| 自定义 | 扩展事件 |

### 4.3 价值与风险

价值：

- 前端不需要理解每个后端的私有流格式；
- 状态同步（快照 + 增量）有标准做法；
- 人机协同中断有一等表示。

风险：

- 事件数量多，前端实现成本不低；
- 状态增量需要严格顺序与去重；
- 与后端 journal 的关系必须明确：AG-UI 事件是投影，不是事实源。

本文判断：如果已有自定义流协议且前端稳定，不必为了“标准”迁移；如果要支持多种后端或第三方前端，AG-UI 值得采用。

## 5. Agent Protocol 与厂商 API

Agent Protocol（AI Engineer Foundation 提出）定义了一组通用 HTTP 接口：创建任务、查询状态、获取产物、取消等。它更接近“Agent 即服务”的 REST 约定。

厂商平台 API 通常提供：

- 运行时（容器/无服务器）；
- 会话与记忆；
- 身份与凭证；
- 工具网关；
- 可观测性。

采用前必须确认：

1. 状态能否导出？
2. 身份是否绑定平台？
3. 权限模型是否可映射到本地策略？
4. 迁移到自建或其他平台的成本？
5. 配额、区域、合规限制？

## 6. 协议选择矩阵

| 需求 | 首选 | 备选 |
|---|---|---|
| 接入外部工具 | MCP | 自定义 HTTP 工具 |
| 跨组织代理协作 | A2A | 自定义任务 API |
| 多后端前端统一 | AG-UI | 自定义 SSE |
| 对外暴露 Agent 服务 | Agent Protocol / A2A | 自定义 REST |
| 托管运行时 | 云平台 | 自建 |
| 观测 | OpenTelemetry GenAI | 自建 trace 格式 |

## 7. 互操作反模式

1. **第二事实源**：平台会话与本地 journal 同时作为权威，恢复时不知信谁。
2. **能力假设**：假设所有 MCP server 都支持并行调用或取消。
3. **协议当权限**：以为接了 MCP 就有了访问控制。
4. **版本漂移**：不固定协议版本，server 升级导致行为变化。
5. **事件重复**：推送与流式同时到达，未去重。
6. **状态双写**：前端状态与后端状态各自演化，最终不一致。
7. **错误吞掉**：把协议错误映射成通用失败，丢失可恢复信息。
8. **过度标准化**：内部单进程通信用 A2A，增加序列化与延迟。

## 8. 接入检查清单

引入任何协议前：

- [ ] 它属于哪一层（工具、协作、UI、观测）？
- [ ] 它是否引入新的状态存储？谁权威？
- [ ] 它是否引入新的身份体系？如何映射？
- [ ] 它的错误模型能否映射到本地错误分类？
- [ ] 它的版本策略与兼容承诺是什么？
- [ ] 它是否要求暴露内部数据？范围多大？
- [ ] 断连、超时、重试、去重如何处理？
- [ ] 有没有可替换的本地实现？

## 9. 成熟判据

- [ ] 协议边界清晰，不跨越职责；
- [ ] 状态权威唯一，协议层只做投影或传输；
- [ ] 协议版本固定并记录；
- [ ] 外部输入默认不可信；
- [ ] 错误、超时、重试、去重有统一处理；
- [ ] 凭证不通过协议明文传递；
- [ ] 有协议级的集成测试与故障注入；
- [ ] 迁移路径明确，不被单一平台锁定。
