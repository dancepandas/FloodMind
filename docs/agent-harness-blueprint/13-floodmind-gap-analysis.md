# 13. FloodMind 差距分析

> 所属：Agent Harness 建设蓝图 / 第三部分 对照与采用
> 版本：v1.0-draft（2026-10-18）
> 证据基线：`docs/knowledge-graph/`（当前实现）、`docs/architecture/FM_ARCHITECTURE_BASELINE.md`（目标契约）、本目录 `12-maturity-model.md`（评分标准）
> 原则：只把“代码中可验证的事实”和“基线中显式声明的目标”作为依据；“业界这么做”不作为扣分理由。
> 闭合状态：见 [15-gap-closure-status.md](./15-gap-closure-status.md)。2026-10-18 审计时，G-01..G-22 已全部闭合或显式决策；本文保留为差距分析的初始快照。

## 1. 结论摘要

FloodMind 的结构性成熟度约为 **L2（可恢复）**，部分维度达到 L3 的特征；运营性成熟度约为 **L1-L2**，主要受评测与可观测性拖累。

更准确的说法是：

- **控制面与状态面的骨架已经具备**：canonical Journal、确定性 reducer、检查点与恢复、工具事务、权限服务、子线程与后台任务、产物内容寻址。这在业界同类项目中属于较完整的设计。
- **能力面的“声明与执行”存在脱节**：能力表、重试建议、上下文窗口、工具注册、技能写入校验等，设计存在但未完全消费或未接线。
- **保障面明显不足**：仓库内未见 CI 配置、没有内部评测集、没有指标与 OTel 语义、没有故障注入测试。这直接限制了对前两部分的信心。
- **不建议在当前阶段引入多代理或平台化**：结构性缺口未闭合前，增加组件只会放大故障。

## 2. 评分总表

| 维度 | 当前等级 | 判断 | 主要依据 |
|---|---|---|---|
| D1 控制循环 | L2 | 循环有界性弱、预算缺失 | `max_iterations=10000`；abort 在模型/工具边界生效；无 token/金额预算 |
| D2 状态与持久化 | L2（接近 L3） | 骨架完整，fencing 未闭合 | Journal + reducer + checkpoint + resume + reconcile；lease 不校验写入 |
| D3 工具与 ACI | L2 | 契约完整，输出与评测不足 | ToolSpec、校验、权限；无输出卸载与工具评测集 |
| D4 上下文工程 | L1-L2 | 有压缩，缺预算与卸载 | Atomic Group 压缩；窗口来源不一致；无卸载/渐进披露 |
| D5 权限与沙箱 | L2 | 有策略与审批，缺凭证隔离 | PermissionService、deny 规则、子代理限制；无凭证代理 |
| D6 记忆与知识 | L2-L3 | 管线完整，治理不足 | 四类操作、语义库、核心记忆、经验树；无失效/遗忘/独立评测 |
| D7 模型网关 | L1-L2 | 多 provider，能力层空转 | codec 齐全；能力表、重试建议、超时、计量存在缺口 |
| D8 规划与多代理 | L2 | 子线程可用，缺规划产物与收益证据 | 子线程配额、specialist registry；无计划文件/对比基线 |
| D9 协议与互操作 | L2 | MCP 可用，配置与信任待收口 | MCP pool、LoadMcpServer；两份 mcp.json；无 A2A/AG-UI |
| D10 评测与可观测性 | L1 | 只有追踪文件与单元测试 | `trace.jsonl`；未见 CI 配置、无金标集、无指标 |

总体取短板：**L1**（受 D10 与 D7 限制）；按“结构与安全”单独看：**L2**。

## 3. 逐维分析

### D1 控制循环

已有：

- 原生 Agent 循环，含流式、工具调用、并行工具 future；
- 中断感知：每 0.5s 检查 abort，取消未完成 future 并标记 interrupted [B: `floodmind/agent/native/native_flood_agent.py:2381-2387`]；
- 子线程默认 `max_turns=50`、`wall_clock_budget_seconds=300` [B: `native_flood_agent.py:426-428`]；
- 工具调用有 journal 事件与终态。

差距：

1. 主循环 `max_iterations=10000` [B: `native_flood_agent.py:331`]，实际上等于无界；没有“无进展检测”。
2. 没有 token 或金额预算的执行点；成本只能在事后统计。
3. 模型请求重试不可中断：3 次、2s→30s 退避，abort 后仍等待 [B: `docs/knowledge-graph/07-model-layer.md` 6]。
4. 停止原因没有统一的封闭枚举；不同路径的终态语义需核对。

判断：达到 L2 的“可停止、可取消”，未达到 L3 的“预算可执行、重试可中断”。

### D2 状态与持久化

这是 FloodMind 最强的部分。

已有：

- Journal 为唯一权威，reducer 确定性派生 RunState [B: `docs/knowledge-graph/04-runtime-kernel.md` 2-4]；
- 检查点含游标、reducer 版本、工具注册表版本、五段身份，原子 rename [B: 6.1]；
- 恢复流程完整：租约 → 校验 → 重放 → 对账 → 再重放 → resume 事件 [B: 6.2]；
- 僵尸事务落定为 `indeterminate` 并补 `tool.result.committed(failed)` [B: 6.2]；
- 子线程、后台任务、产物均有独立生命周期与对账逻辑。

差距：

1. **fencing 未闭合**：lease 只是入场锁，JournalWriter 的 append 不校验 epoch，旧 owner 迟到写入仍可成功 [B: 6.3]。这是 P0 级正确性风险。
2. 文件回滚未实现（`rollback_files` 为 legacy）[B: 6.1]；恢复后工作区可能处于半完成状态。
3. 缺少故障注入测试证明恢复语义；现有测试以单元为主。
4. 检查点与 journal 的一致性校验依赖逐字段比较，规模大时成本需评估。

判断：设计达到 L3，证据与 fencing 拉回 L2。

### D3 工具与 ACI

已有：

- `ToolSpec` 契约、参数校验、权限判定、工具目录（tool catalog）与按需发现；
- 每个 Agent 使用 `_InstanceToolRegistry`，避免全局注册表串台 [B: `docs/knowledge-graph/06-tools-skills-mcp.md`]；
- MCP 工具名做过 sanitize（`mcp_server_tool`），避免非法字符；
- CreateSkill 有读回校验与回滚。

差距：

1. 输出上限与卸载：`_finalize_tool_output` 只做重试保护，不做截断或卸载；大结果会直接进入上下文 [B: `06-tools-skills-mcp.md`]。
2. 部分工具未在 native runtime 注册：`MemoryAdd`、`ApplyPatch` 不在 `all_tools` 中 [B: `native_flood_agent.py:876-892`]；`full_ref` 无生产者。
3. `UpdateSkill` 没有读回校验，写入失败可能留下半成品。
4. 没有工具评测集；工具描述变更无回归依据。
5. 工具数量增长后没有动态裁剪策略（有 catalog，但暴露规则需核对）。

判断：契约层 L2，评测与上下文效率未达 L3。

### D4 上下文工程

已有：

- `ContextCompressor`，保留头尾、按 Atomic Group 删除中间段、发出压缩事件 [B: `docs/knowledge-graph/03-agent-execution.md` 6]；
- 提示词分层清晰（全局、项目、会话、模型、宿主、记忆）[B: 03 第 5 节]；
- 上下文块有预算截断机制 [B: `floodmind/agent/context_runtime.py:222-248`]。

差距：

1. 压缩触发阈值与硬预算使用不同窗口来源；能力注册表默认不设置 `context_window`，回退到执行器窗口 [B: `03-agent-execution.md` 6, `07-model-layer.md` 5]。结果是压缩时机不可靠。
2. 压缩后必须生成摘要，但区间计算失败时可能直接丢弃中间段且无摘要 [B: 03 第 6 节]。
3. 没有大结果卸载与引用读取；没有渐进披露（工具目录是部分实现，但知识/文件未做）。
4. 没有稳定前缀的缓存布局治理；没有缓存命中指标。
5. 没有记录“模型当时看到的完整上下文”，回放能力弱。
6. `AGENTS.md` 从 `Path.cwd()` 读取，而非 workspace 根目录；宿主从其他目录启动时项目规则可能缺失或取错 [B: 03 第 5 节]。

判断：L1-L2。压缩有了，但预算、卸载、回放三项缺失，使其无法稳定支撑长任务。

### D5 权限与沙箱

已有：

- `PermissionService`，支持规则、deny、ASK 两条路径 [B: `docs/knowledge-graph/04-runtime-kernel.md` 5.2]；
- 子代理有显式 deny 规则：禁止网页抓取、动态加载 MCP、修改项目指令 [B: `native_flood_agent.py:855-871`]；
- 后台任务与子线程可启用沙箱；
- 产物发布有 allowed roots、symlink resolve、大小与哈希校验 [B: 04 第 7.3 节]。

差距：

1. 默认是否 fail-closed 需核对：未匹配规则时是询问还是允许，直接决定安全下限。
2. 没有凭证代理；密钥可能存在于配置或环境中，沙箱内代码可能读取。
3. 沙箱只有“可选启用”，没有按动作风险分级；没有网络默认关闭策略。
4. `allowed_roots` 为空时不做源文件 containment 检查；生产装配必须显式传入 [B: 04 第 7.3 节]。
5. 没有注入用例库、越权测试、红队演练。
6. 缺少不可篡改审计与访问控制；trace 与审计未分离。

判断：L2。策略层有，凭证与沙箱分层未达 L3。

### D6 记忆与知识

已有：

- 十层记忆结构，职责清晰 [B: `docs/knowledge-graph/05-memory.md` 2]；
- 固化管线：ADD/UPDATE/DELETE/NOOP，先检索相似项再判定 [B: 05 第 4 节]；
- 语义事实存储支持软失效/软删除；核心记忆项目级；经验树与技能草案有生成门槛；
- `MemoryServices` 统一门面，旧 LTM 导入语义库并去重。

差距：

1. `MemoryAdd` 未在 native runtime 注册，模型无法主动写入 [B: `native_flood_agent.py:876-892`]；只有显式调用门面才走该路径。
2. 没有时间有效性（双时间）与遗忘/衰减；长期运行会累积陈旧事实。
3. 没有记忆质量指标（写入精确率、过期残留率、冲突处理正确率）。
4. 回顾与固化依赖 LLM 判定，判定失败时的丢弃策略已有，但缺少可观测与回放。
5. 技能生成有门槛，但缺少生成后的质量评估与回滚。
6. `global_search` 无调用方，已在 2026-10-19 遗留内容清理中删除。

判断：L2-L3。管线完整，治理与评测不足。

### D7 模型网关

已有：

- 多 provider codec：dashscope、deepseek、kimi、minimax、openai_compatible，Anthropic 在 transport 内；
- `resolve_model()` 统一配置解析，优先级明确；
- 流式与非流式两条调用链；
- 客户端缓存。

差距（均来自知识图谱风险表 [B: `07-model-layer.md` 6]）：

1. 能力表空转：默认注册表不设置 `context_window`，其他能力位不消费。
2. 重试建议字段 `response_started` / `replay_safe` 从未赋值，无法判断重试安全性。
3. LLM 超时硬编码 90s；重试不可中断。
4. 两套 `TokenUsage`，富模型未被使用，用量字段可能丢失。
5. 路由前缀漏配（DashScope 不含 `qwen`）；模型 ID 可跨 provider 冲突。
6. API key 明文存储；缓存键使用无盐 MD5。
7. `.env.example` 的优先级说明与实现相反。
8. Anthropic 校验不完整。

判断：L1-L2。多供应商是优势，但“能力、重试、计量”三项未形成可靠契约。

### D8 规划与多代理

已有：

- 子线程/子代理：独立 journal、沙箱 workspace、子权限上下文、独立工具运行时、turn/token/wall-clock 配额、产物回传 [B: `04-runtime-kernel.md` 7.2]；
- specialist registry 与 orchestrator registry 分离，专家工具集受限于安全白名单 [B: `native_flood_agent.py:913-919`]；
- 任务工具（task_output/list/kill）与后台任务管理。

差距：

1. 没有显式的计划产物（计划文件、待办结构、验收标准）；规划完全依赖模型在上下文内维持。
2. 子代理输入输出没有结构化契约（目标、范围、约束、验收、预算、返回格式）。
3. 没有“单代理 vs 多代理”的对比数据；无法判断拆分是否带来净收益。
4. 取消父 run 时子线程与后台任务的传播需验证；孤儿进程清理有不稳定路径（清理失败时终态降级）。
5. 没有编排-工人之外的模式支持（评估-优化、handoff 作为一等原语）。

判断：L2。机制在，规划与收益证据不足。

### D9 协议与互操作

已有：

- MCP 客户端池、动态 `LoadMcpServer`、工具注册与卸载对称；
- 工具名 sanitize；
- 技能注册表与 curator。

差距：

1. 两份 `mcp.json`：运行时读 `~/.floodmind/mcp.json`（`transport` 字段正确）；项目 `.floodmind/mcp.json` 使用 `type`，默认不加载 [B: `06-tools-skills-mcp.md`]。这是易错点，应在文档与错误提示中显式区分。
2. MCP 返回内容未做“不可信输入”标记与注入筛查。
3. 没有协议版本记录与握手能力校验。
4. 没有 A2A / AG-UI；前端事件为私有格式（这本身不是缺陷，但限制了第三方接入）。

判断：L2。能用，但信任与版本治理未收口。

### D10 评测与可观测性

已有：

- `TracingService`：每 session 内存缓冲 span/event，flush 到 `trace.jsonl` [B: `04-runtime-kernel.md` 7.4]；
- 约 122 个测试文件、千余测试；使用 `parametrize` 与 `skipif`。

差距：

1. 仓库内未见 CI 工作流；测试不在提交或发布时自动运行。
2. 没有测试分类（单元/集成/慢测试），也没有自定义 marker；无法按层选择。
3. 没有内部评测集、金标集、轨迹评测。
4. 没有指标体系（成功率、工具错误率、成本、时延分位）。
5. trace 是文件，未遵循 OTel GenAI 语义；没有跨 run 查询与聚合。
6. trace 路径在未传 base 时使用 `Path.cwd()/data/sessions`，与 Journal 的显式 runtime root 策略不一致 [B: 04 第 7.4 节]。
7. 没有故障注入测试（崩溃、网络中断、超时后成功）。

判断：L1。这是总体等级的主要短板。

## 4. 契约层核对（C1-C6）

| 契约 | 状态 | 说明 |
|---|---|---|
| C1 身份 | 基本具备 | 五段身份进入检查点；需核对子线程/后台任务/产物是否共用同一身份族 |
| C2 消息 | 具备 | 保留 provider 原生块；需核对跨 provider 归一是否丢失思考/用量 |
| C3 工具 | 部分 | ToolSpec 完整；输出上限、幂等声明、重试语义不完整 |
| C4 事件 | 具备 | append-only、序号、类型、payload 版本；需核对事件类型封闭性与版本迁移 |
| C5 状态 | 具备 | reducer + projection；需核对 reducer 版本升级策略 |
| C6 策略 | 部分 | 规则与 ASK 存在；需核对 deny 优先级、默认 fail-closed、审批指纹绑定 |

## 5. 缺口清单

按“先正确性与安全，再契约，再效率，再扩展”排序。

### P0（正确性或安全边界）

| 编号 | 缺口 | 影响 | 建议 |
|---|---|---|---|
| G-01 | Journal 写入不校验 lease epoch | 旧 owner 迟到写入，状态分叉 | 写入携带 epoch，服务端拒绝旧 epoch |
| G-02 | 模型重试不判断响应是否已开始 | 重复输出、重复扣费 | 填充 `response_started`/`replay_safe`，并让取消打断退避 |
| G-03 | 上下文窗口来源不一致、能力表不设窗口 | 压缩时机错误，长任务失败 | 单一窗口来源，启动时校验 |
| G-04 | 压缩可能无摘要丢弃中间段 | 语义丢失，任务跑偏 | 摘要失败即中止压缩并保留原文 |
| G-05 | 默认权限行为未证明 fail-closed | 未匹配规则可能放行 | 加测试固定默认行为；deny 绝对优先 |
| G-06 | 凭证可能进入沙箱/配置明文 | 提示注入可窃取 | 凭证代理 + 加密存储 + 沙箱不继承环境 |
| G-07 | 未见 CI，且无故障注入测试 | 恢复与安全语义无证据 | 最小 CI：单元 + 关键故障注入 |

### P1（契约与可运营性）

| 编号 | 缺口 | 影响 | 建议 |
|---|---|---|---|
| G-08 | 工具输出无上限/卸载 | 上下文被单次结果打爆 | 阈值 + 摘要 + 引用 + 读取工具 |
| G-09 | `MemoryAdd` 未在 native 注册 | 模型无法主动记忆 | 明确产品决策：注册或移除文档承诺 |
| G-10 | `UpdateSkill` 无读回校验 | 半成品技能 | 与 CreateSkill 对齐 |
| G-11 | 两份 mcp.json 语义不同 | 配置不生效且难排查 | 统一格式或启动时显式报错 |
| G-12 | 上下文无法回放 | 无法定位“模型当时看到什么” | 记录装配快照或可重建引用 |
| G-13 | trace 无指标、非 OTel | 无法聚合与告警 | 采用 OTel GenAI 语义，补指标 |
| G-14 | 无内部评测集与回归门禁 | 变更无法判断好坏 | 冒烟集 + 回归集 + CI 门禁 |
| G-15 | 记忆无失效/遗忘 | 陈旧事实累积 | 加 `valid_to` 与衰减 |
| G-16 | 子代理无输入输出契约 | 汇总质量不稳定 | 结构化任务包与返回格式 |

### P2（效率与扩展）

| 编号 | 缺口 | 影响 | 建议 |
|---|---|---|---|
| G-17 | 无工具评测集 | 工具描述无法优化 | 真实任务集 + 轨迹指标 |
| G-18 | 无 token/金额预算 | 成本不可控 | 预算检查点 + 明确终态 |
| G-19 | 无路由与回退 | 成本/质量无法权衡 | 按任务类型路由，记录回退 |
| G-20 | 无渐进披露 | 工具/知识挤占预算 | 索引 + 按需加载 |
| G-21 | 无 A2A/AG-UI | 第三方接入受限 | 有需求再引入，不预先建设 |
| G-22 | 无多代理收益基线 | 无法判断是否值得拆分 | 选定 3-5 个任务做对比 |

## 6. 与目标基线的关系

`FM_ARCHITECTURE_BASELINE.md` 已经定义了完整的目标契约与不变量。本分析不重复其条目，只指出三类关系：

1. **已实现但未验证**：Journal、reducer、checkpoint、resume、工具事务。代码存在，缺少故障注入与 CI 证据。
2. **已声明但未接线**：能力表、重试建议、`MemoryAdd`、`full_ref`、部分配置项。声明存在，运行时未消费。
3. **未覆盖**：评测体系、成本预算、凭证代理、上下文回放、记忆失效。

这三类需要不同的处理方式：第一类补测试，第二类做接线或删除声明，第三类排入路线。

## 7. 不建议现在做的事

| 想法 | 为什么不建议 |
|---|---|
| 引入多代理框架 | 子代理机制已有；缺的是契约与收益证据，不是框架 |
| 用 LangGraph 替换现有循环 | 会丢失已有 journal/reducer 语义，收益不明确 |
| 接入托管平台记忆 | 会把状态与身份移到外部，与“唯一事实源”冲突 |
| 上 A2A/AG-UI | 当前没有跨组织或第三方前端需求 |
| 重写上下文系统 | 应先补预算、卸载、回放三个点，而不是换实现 |
| 追求 OTel 全量语义 | 先有指标与关联 ID，再谈语义约定 |

## 8. 评估方法与局限

- 本分析基于 `docs/knowledge-graph/` 的快照与对关键代码的抽查，未做全量代码审计。
- 等级判断是结构性判断，不是质量评分；同一等级内差异可能很大。
- 未运行测试套件，因此“测试存在”不等于“测试通过”。
- 未做生产数据分析，成本与时延结论为定性。
- 建议在启动路线图前，用 `12-maturity-model.md` 的评分卡做一次带证据的正式评估，并由代码所有者复核。
